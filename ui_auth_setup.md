# Лабораторная №5, раздел 6.2: вход в Blazor InteractiveServer

После завершения шага 6 все три страницы переведены на REST API, API доступен во всех средах с прежней проверкой JWT и ролей, добавлен единый переключатель InMemory/PostgreSQL. Актуальная инструкция запуска — [backend_documentation.md](backend_documentation.md). Описание границ 6.2 ниже является историческим.

## Что реализовано

Вход через электронную почту и пароль существующего пользователя Supabase Auth. Отдельная схема `Equipment.Ui` выдаёт защищённую cookie `__Host-EquipmentManager.Session`: Secure, HttpOnly, SameSite=Lax, Path=/, без Domain, без скользящего продления. Cookie защищается ASP.NET Core Data Protection и содержит UUID пользователя, имя и случайный ID локального сеанса; пароль, access token и refresh token в неё не попадают.

Страница `/login` использует static SSR (`ExcludeFromInteractiveRouting`). Вход `/account/login` и выход `/account/logout` выполняются обычными HTTP POST с antiforgery, без enhanced submit. После входа происходит полная навигация и создаётся новый SignalR circuit с cookie. Все страницы приложения, кроме страницы входа, требуют интерфейсной аутентификации как при HTTP SSR, так и при интерактивной маршрутизации. Пароль существует только во входящем POST и серверном запросе Auth, не восстанавливается в форме после ошибки и не сохраняется приложением.

Access token хранится только в памяти серверного процесса с абсолютным сроком не больше срока JWT и восьми часов. **Refresh token не сохраняется, автоматического refresh нет: по истечении нужен повторный вход.** Это выбранный допустимый режим завершения короткого сеанса. Cookie непостоянная (без «запомнить меня»). Перезапуск приложения инвалидирует все локальные сеансы, даже если браузер восстановил cookie.

JWT ответа Auth криптографически проверяется с существующими issuer, audience, алгоритмом, сроком и доверенным JWKS. Дополнительно проверяются sub UUID, role=authenticated и отсутствие anonymous-входа; профиль должен быть активным с одной из существующих бизнес-ролей. Из JWT/user_metadata бизнес-роли для приложения не назначаются. При неизвестном ключе запрашивается обновление доверенного JWKS; невалидный токен не принимается.

Backend API сохраняет существующие **явно заданные Bearer-политики** и проверку актуального профиля в PostgreSQL: cookie сама по себе API не авторизует. Новый scoped `SessionBackendClient` получает principal из AuthenticationStateProvider, проверяет серверный сеанс и отправляет JWT в Authorization отдельного HTTP-запроса к доверенному BackendBaseUrl. HttpClient не хранит токен в общих DefaultRequestHeaders, не принимает cookies и не следует редиректам. Токены не копируются между пользователями. Истёкший/отозванный локальный сеанс блокирует запрос до отправки; ответ API 401 отзывает локальный сеанс и требует входа.

Провайдер состояния Blazor проверяет существование/срок серверного сеанса каждые 15 секунд. Выход в одной вкладке отзывает её общий ID на сервере; остальные circuits обновляются в пределах этого интервала и переходят ко входу. Каждый вызов нового API-клиента проверяет сеанс непосредственно, без ожидания таймера. Уже отправленный запрос может успеть завершиться.

Выход удаляет локальный сеанс и cookie, затем вызывает Supabase `/logout?scope=local`. При сетевой ошибке локальный выход сохраняется, интерфейс честно сообщает, что удалённый выход не подтверждён. Как и у обычных Supabase JWT, уже выданный и отдельно скопированный access token может приниматься Bearer API до exp; локальный отзыв не является JWT denylist. Профиль/роли API проверяет на каждом запросе как прежде.

Серверное хранилище рассчитано на **один процесс**; для нескольких экземпляров потребуется общее защищённое хранилище сеансов и общие Data Protection keys. Сейчас новых хранилищ/пакетов/таблиц не добавлено.

## Границы раздела 6.2 (состояние на момент его выполнения)

Страницы оборудования, заявок и истории и их сервисы хранения не менялись: они продолжают работать с общими демонстрационными данными в памяти. Вход закрывает анонимное открытие страниц, но перенос операций этих страниц на API и применение бизнес-разрешений к их старым прямым вызовам относятся к следующему этапу. Проверку JWT/ролей существующего API это не ослабляет. Не использовать демонстрационный режим для реальных рабочих данных.

Страница `/account/session` показывает имя и кнопку «Проверить доступ к API», которая выполняет настоящий GET существующего `/api/equipment` через серверный клиент и выводит только число записей. Она не изменяет данные. API по-прежнему опубликован только в Development; в других средах проверка покажет недоступность, как и до этой работы. Истечение cookie не продлевает JWT и не обновляет SignalR principal скрыто.

Логирование HTTP-клиентов Auth/Backend отключено; ответы Auth, пароли, JWT и ключи не включаются в сообщения исключений интерфейса. localStorage/sessionStorage для авторизации не используются. Не включайте внешнее журналирование тел/заголовков запросов `/account/login` и Supabase Auth в прокси, APM или отладчике. Обычный password manager браузера управляется пользователем, приложение его хранилище не использует.

## Настройка и ручная проверка в Visual Studio

1. Открыть `EquipmentManager.sln`, выбрать EquipmentManager запускаемым проектом. В панели запуска выбрать профиль **https** из существующего `Properties/launchSettings.json`, не `http`. Его адрес — `https://localhost:7128`. При первом запуске подтвердить стандартное предложение Visual Studio доверять локальному сертификату разработки. Secure cookie по HTTP работать не будет.
2. Убедиться, что существующие SupabaseAuth:Enabled/SettingsConfirmed/Issuer/Audience/SigningAlgorithm настроены для уже используемого проекта. Эти настройки и настройки Supabase в данной работе не изменялись.
3. ПКМ по проекту → **Управление секретами пользователя / Manage User Secrets**. Сохранить прежний `ConnectionStrings:Profiles` и остальные значения, добавить раздел (не заменять весь файл):

```json
"SupabaseUiAuth": {
  "PublishableKey": "<существующий publishable key или legacy anon key этого проекта>",
  "BackendBaseUrl": "https://localhost:7128/"
}
```

Заменить placeholder только локально, реальный ключ в репозиторий/чат не копировать. Допускается `sb_publishable_...` или legacy JWT с role=anon; `sb_secret_...` и service_role запрещены. Даже публичный клиентский ключ здесь используется только сервером. Новые ключи/пользователей/настройки в Supabase создавать не требуется. Альтернатива User Secrets — переменные окружения `SupabaseUiAuth__PublishableKey`, `SupabaseUiAuth__BackendBaseUrl` и существующая `ConnectionStrings__Profiles`. Ключ читается только из User Secrets/окружения, не из appsettings. BackendBaseUrl — доверенный HTTPS origin с завершающим `/`; не вычисляется из пользовательского Host/returnUrl.

4. Использовать **уже существующего** тестового пользователя Supabase с известным паролем и активным профилем engineer/maintenance_specialist/manager. Никакие пользователи/профили автоматически не создаются и не меняются. Не использовать учётную запись администратора БД как пользователя входа.
5. Запустить F5, открыть `https://localhost:7128/account/session` в приватном окне. Ожидается перенаправление на `/login` с сообщением о необходимости входа. Ввести неверный пароль: появится понятная ошибка, пароль очистится, cookie сеанса не создастся.
6. Ввести правильные данные. Ожидаются имя пользователя и рабочее пространство. При прямом открытии `/login` после успеха по умолчанию открывается `/account/session`; при переходе с защищённой страницы возвращается исходный локальный адрес.
7. На странице **«Сеанс»** нажать **«Проверить доступ к API»**. Ожидается «API доступен. Получено записей оборудования: …». Это подтверждает серверную передачу Bearer JWT и прежнюю проверку роли Backend. При недоступности Profiles/Backend появится ошибка, не ложный успех. Проверьте, что BackendBaseUrl совпадает с HTTPS-портом запуска, если профиль меняли.
8. Открыть вторую вкладку того же браузера, затем нажать **«Выйти»** в первой. Ожидается страница входа с подтверждением; повторное открытие защищённой страницы требует входа. Вторая подключённая вкладка переходит ко входу в течение примерно 15 секунд. При недоступном Auth будет отдельное сообщение о неподтверждённом удалённом выходе, но локальный вход уже отозван.
9. Для проверки срока без изменения Supabase: войти и дождаться exp существующего JWT (не изменять настройки проекта). Следующий API-запрос/HTTP-переход либо проверка circuit потребуют повторный вход. Более быстрый ручной вариант — остановить и снова запустить приложение: старый серверный сеанс исчезнет и потребуется вход. Автоматические тесты проверяют exp с управляемыми часами без ожидания.
10. При необходимости проверить DevTools → Application → Cookies: есть Secure/HttpOnly cookie сеанса, нет access/refresh token в localStorage/sessionStorage. Не копировать cookie или форму с паролем в логи/отчёт. Сетевой браузерный трафик содержит только POST формы на собственный сервер; запросы к Auth и API с JWT выполняются сервером.

При отсутствии клиентского ключа будет сообщение о настройке; при отсутствии/неактивности профиля — отказ доступа; при сбое профилей/сети — отдельная ошибка. Если форма устарела (например, вход/выход изменился в другой вкладке), обновить её перед повторной отправкой. Пароль восстановлению из ответа сервера не подлежит.

## Автоматическая проверка

Команды из каталога решения:

```powershell
dotnet build EquipmentManager.csproj --no-restore
dotnet test EquipmentManager.Tests/EquipmentManager.Tests.csproj --no-restore
```

Пакеты не устанавливались. Новые тесты запускают локальный Kestrel и static SSR страницы входа, подменяют только транспорт Supabase/JWKS и источник профилей. HTTPS termination имитируется исключительно тестовым middleware; в рабочем приложении такой подмены нет. Проверяются antiforgery, cookie-флаги, отсутствие JWT в cookie/HTML, неверные учётные данные/JWT/срок, сетевой отказ, профиль, открытый redirect, локальный/удалённый выход, replay старой cookie, истечение, отзыв circuit, передача JWT в настоящий локальный API и его 401. Прежние тесты JWT/ролей и бизнес-сервисов сохраняются.

Фактический результат локальной проверки: сборка успешна, 0 предупреждений и 0 ошибок; все 74 теста прошли (19 новых UI-сценариев и 55 прежних), пропусков нет. Проверка выполнялась с `--no-restore` и не устанавливала пакеты.

Фактический вход в реальный Supabase и ручное управление браузером в этом этапе не выполнялись: пользовательские учётные данные не предоставлялись, тесты изолированы от облака. Результаты автоматических тестов не выдаются за облачную интеграционную проверку. SQL, миграции и проекты Supabase не изменялись; commit/push не выполнялись.
