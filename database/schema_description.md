# Лабораторная №5. Проект базы данных EquipmentManager

## Назначение и границы

Схема `schema.sql` подготовлена по `technical_specification.md`, `user_stories.md`, `AGENTS.md`, всем трём моделям, `EquipmentDataService`, `FaultDataService`, `EquipmentValidator` и поиску в `EquipmentList.razor`. Это проект постоянного хранения для будущего подключения; приложение по-прежнему использует память. Код и пакеты не изменяются.

Целевая среда — PostgreSQL в Supabase с существующими `auth.users(id uuid)` и ролями `anon`, `authenticated`. На обычном PostgreSQL без Supabase скрипт не автономен: требуется предварительно выбрать другой поставщик идентификации и адаптировать FK/роли, а не создавать фиктивную таблицу паролей. Скрипт транзакционный, рассчитан на однократное применение в новой схеме, не является повторяемой миграцией; `CREATE OR REPLACE`/удаления существующих объектов нет. Расширения не устанавливаются. Сам скрипт в рамках работы не выполнялся.

## Сущности и связи

Уточнение совместимости Supabase: начальный блок schema.sql проверяет наличие Auth, ролей и конфликтующих объектов; повторная установка отклоняется до DDL с понятным сообщением. Скрипт остаётся однократным, не миграцией. Инструкции и проверки: [supabase_setup.md](supabase_setup.md).

| Таблица | Ключ | Назначение и связи |
| --- | --- | --- |
| `equipment` | `id integer identity` | Имя, инвентарный номер, вычисляемый нормализованный номер, место установки, техническое состояние |
| `faults` | `id integer identity` | Оборудование, снимок его подписи, проблема, статус, автор регистрации, авторы начала и завершения, даты, работы, результат, версия |
| `maintenance_records` | `fault_id integer` | Одна неизменяемая запись на завершённую заявку; оборудование, подпись, дата, работы, результат, исполнитель |
| `profiles` | `id uuid`, одновременно FK | Дополнение к `auth.users`: отображаемое имя, набор назначенных ролей и признак активности |

Связи: `auth.users` 1 → 0..1 `profiles`; `profiles` 1 → N заявок по каждому из трёх авторов; `profiles` 1 → N записей обслуживания по исполнителю; `equipment` 1 → N `faults`; `equipment` 1 → N `maintenance_records`; `faults` 1 → 0..1 `maintenance_records` (для завершённой заявки — ровно 1).

Составной FK истории `(fault_id, equipment_id)` ссылается на UNIQUE `(id, equipment_id)` заявки. Поэтому история не может указывать оборудование другой заявки. Прямой FK истории на оборудование дополнительно выражает политику его удаления. Снимок подписи не изменяется при будущем переименовании оборудования.

## Согласование с C#

| Модель / свойства | PostgreSQL / преобразование |
| --- | --- |
| `Equipment.Id`, `Fault.Id`, обе `EquipmentId`, `MaintenanceRecord.FaultId` | `integer` → `int`; положительные identity ID оборудования и заявок; собственный ID истории не добавляется |
| `Equipment.Name`, `InventoryNumber`, `Location`, `Status` | `name`, `inventory_number`, `location`, `status`, обязательный `text` |
| `Fault.EquipmentLabel`, `Description`, `Status`, `Version` | `equipment_label`, `description`, `status`, `version`; начальная версия 1 |
| `Fault.Author` | При чтении формируется из `profiles.display_name` по `created_by`; строка имени не является идентификатором пользователя |
| `Fault.CreatedAt`, `StartedAt?`, `CompletedAt?` | `timestamptz`, `timestamptz NULL`, `timestamptz NULL` → `DateTimeOffset`, `DateTimeOffset?`; будущий адаптер возвращает UTC с offset 0 |
| `Fault.WorkDescription`, `Result` | `NOT NULL text DEFAULT ''` до завершения; непустые после завершения |
| Все свойства `MaintenanceRecord` | Одноимённые столбцы snake_case; `performed_at` → UTC `DateTimeOffset` |
| Поля без текущих свойств моделей | `normalized_inventory_number` вычисляется БД; `created_by`, `started_by`, `completed_by`, `performed_by` — UUID (`Guid`); профиль пока не имеет модели C# |

`FaultRegistration` и `FaultCompletion` — входные данные команд, отдельных таблиц для них нет. При будущем подключении нужен явный mapper snake_case и проекция автора; текущие классы не объявляются готовыми ORM-сущностями. Схема сохраняет текущие типы и семантику, но не является заменой реализации адаптера.

Допустимые состояния оборудования точно взяты из `Equipment.AllowedStatuses`: `Исправно`, `Требует обслуживания`, `Неисправно`. Статусы заявки: `Новая`, `В работе`, `Завершена`. Они различны по смыслу; изменение заявки не меняет техническое состояние автоматически.

## Целостность, даты и завершение

Обязательные строки имеют `NOT NULL` и CHECK на непустое значение после удаления крайних пробельных символов. Длины и формат номера искусственно не ограничены. Названия, номера и описания могут сохраняться в исходном виде; будущий сервис должен по-прежнему удалять крайние пробелы перед записью, как `EquipmentDataService.Save`.

`guard_fault` разрешает создание только новой заявки версии 1. Дата регистрации назначается БД, подпись формируется из существующего оборудования. Последующие UPDATE разрешены только `Новая → В работе → Завершена`; исходные поля регистрации неизменяемы. Начало требует `started_by`, завершение требует `completed_by`, описания работ и результата. Время назначается сервером БД через `statement_timestamp()`; CHECK обеспечивает хронологию. `timestamptz` хранит момент времени, часовой пояс отображения задаётся клиентом; московское время не записывается как время без зоны.

При завершении AFTER-триггер вставляет историю в той же транзакции. Ошибка INSERT откатывает UPDATE заявки; исключения не подавляются. PK `fault_id` исключает вторую историю. Триггер истории допускает только точный снимок завершённой заявки, запрещает UPDATE/DELETE. Завершённая заявка больше не обновляется. Таким образом дублирование работ/результата/подписи в двух таблицах согласовано ограничениями и триггерами и соответствует снимкам текущих моделей.

Будущий сервис НЕ должен отдельно вставлять историю: это уже делает триггер. Для конкуренции он выполняет параметризованный UPDATE с `WHERE id = @id AND version = @expectedVersion AND status = @expectedStatus`; БД увеличивает версию. Ноль изменённых строк требует проверки отсутствия/конфликта. Само наличие столбца `version` не защищает от команды, которая не проверяет ожидаемую версию. Ошибка или потеря ответа не равна доказанному откату: результат следует перечитать. Защита от повторной регистрации новой заявки после потери ответа пока не реализована.

## Номер и поиск

UNIQUE на вычисляемом `lower(trim_whitespace(inventory_number))` отклоняет `INV-1001` / ` inv-1001 `, в том числе при конкурентных INSERT. `trim_whitespace` явно перечисляет Unicode-пробелы, включая табуляцию, переносы строк и неразрывный пробел; внутренние пробелы сохраняются. Уникальность действует при INSERT и UPDATE и не зависит от проверки формы.

Граница согласования: PostgreSQL `lower` зависит от collation БД и не является точным эквивалентом `.NET OrdinalIgnoreCase` из `EquipmentDataService.Save`. Поиск интерфейса использует ещё другую семантику — `CurrentCultureIgnoreCase`. Для лабораторной источником истины выбран нормализованный ключ PostgreSQL. До миграции следует зафиксировать collation и общий алгоритм с тестами латиницы, кириллицы/Ё, турецких I, Unicode-пробелов и составных Unicode-символов. NFC/NFKC и внутренние пробелы схема не нормализует. Нельзя обещать полное совпадение Unicode-сравнений с текущим C#.

Индексы:

- UNIQUE нормализованного номера — точное совпадение и конкурентная уникальность.
- B-tree `lower(name) text_pattern_ops`, `normalized_inventory_number text_pattern_ops` — префиксный поиск по нормализованному тексту; отдельный pattern-индекс номера имеет другое назначение, чем UNIQUE.
- `equipment(status)` — фильтр технического состояния.
- `faults(equipment_id, id DESC)` и `(status, id DESC)` — заявки объекта и очередь по статусу; общий порядок по ID поддерживает PK.
- `maintenance_records(equipment_id, performed_at DESC, fault_id DESC)` — история выбранного объекта от новой к старой.
- Индексы UUID авторов/исполнителей — соединения, отбор и проверка ссылок при административных операциях.

Текущий поиск «по части» требует подстроки `%запрос%`: перечисленные B-tree индексы его не ускоряют. Корректность обеспечивается запросом `lower(name) LIKE @pattern ESCAPE '\' OR normalized_inventory_number LIKE @pattern ESCAPE '\'`, где параметр построен из нормализованного запроса с экранированием `\`, `%`, `_` и добавлением `%` по краям. Фильтр статуса присоединяется через AND, группа OR заключается в скобки. Пустой запрос снимает текстовый фильтр. Для производительности подстроки после измерений предлагаются два GIN-индекса `gin_trgm_ops` расширения `pg_trgm`; они намеренно не включены и расширение не устанавливается согласно DATA-10. Короткие запросы и маленькие таблицы могут всё равно требовать последовательного сканирования. Эффективность проверяется EXPLAIN ANALYZE на целевых данных.

## Supabase Auth, роли и удаление

Паролей, хешей паролей, токенов и ключей в `profiles` нет: входом управляет Supabase Auth. UUID профиля совпадает с PK `auth.users.id`. Профиль создаёт доверенный сервер после регистрации; автоматический signup-триггер не добавлен. Пустой массив ролей означает отсутствие прав; CHECK допускает только `engineer`, `maintenance_specialist`, `manager`, запрещает NULL-элементы и многомерные массивы. Повтор роли не добавляет разрешений. Совмещение ролей представлено массивом, поскольку отдельная таблица UserRole выходит за четыре запрошенные сущности.

Сервер обязан проверить подтверждённый сеанс, `is_active`, роли и передать фактический UUID автора, а не принять его из формы. Инженер создаёт оборудование; инженер/специалист регистрируют заявку; специалист меняет статус; все три роли читают; руководитель получает сводку. FK подтверждает существование профиля, но не его роль, активность или соответствие сеансу. Скрипт не реализует серверную авторизацию.

Для всех четырёх таблиц включён RLS без разрешающих политик, права `PUBLIC`, `anon`, `authenticated` на таблицы и identity-последовательности отозваны. Прямой доступ через Data API закрыт. Владелец БД и BYPASSRLS/service_role обходят RLS; будущему серверному подключению требуются отдельные права и проверки матрицы. Привилегированные ключи остаются на сервере. RLS-политики для прямого клиентского доступа и самостоятельного редактирования профиля не спроектированы, чтобы не допустить самостоятельную выдачу ролей.

Все FK используют `ON DELETE RESTRICT`: нельзя удалить оборудование с любой заявкой/историей, заявку с историей, используемый профиль или Auth-пользователя с профилем. Каскадного удаления аудита нет. Для отключения пользователя применяется `is_active = false` и блокировка входа в Auth. Полное удаление Auth-пользователя требует отдельного согласованного процесса сохранения/обезличивания аудита. Это сознательно строже распространённого примера Supabase с CASCADE.

Удаление оборудования не входит в семь историй. Физическое удаление несвязанного оборудования технически допускается для доверенного администратора; пользовательский DELETE не предоставляется. Существующий `EquipmentDataService.Delete` удаляет без проверки связей — при подключении это потребуется изменить и обработать FK-отказ. Пока код не изменён. Soft delete/архивирование не добавлены без требования; сроки хранения требуют согласования. Защита рассчитана на обычные DML-операции: владелец может изменить схему, отключить триггеры или выполнить TRUNCATE, поэтому такие права нельзя выдавать приложению.

## Спорные требования и отложенные решения

Функции явно объявлены `SECURITY INVOKER`, повышение прав `SECURITY DEFINER` не используется. Имена таблиц квалифицированы схемой, `search_path` ограничен `pg_catalog`. У всех четырёх функций отозваны права `PUBLIC`, `anon`, `authenticated`, включая выдаваемый PostgreSQL по умолчанию `EXECUTE`. Для будущей непривилегированной серверной роли потребуются отдельно спроектированные права на функции, таблицы, последовательности и RLS-политики; существующие триггеры выполняются с правами вызывающего пользователя. Не следует добавлять `SECURITY DEFINER` только ради обхода RLS или ошибки доступа истории. Отключённая автоматическая выдача прав новым таблицам не является заменой проверки ACL функций.

1. Документы №3 устарели относительно кода: формы, заявки и история уже есть в памяти; источником типов и значений выбраны текущие модели и валидатор. Демонстрационные записи не включены в SQL; авторы `Тестовые данные`/`Не установлен (без авторизации)` не превращаются в пользователей Auth.
2. DATA-02 требует подразделения, отсутствующие в модели Equipment. В пределах четырёх сущностей подразделение и его фильтр не реализованы; выводить его из Location нельзя. Нужны отдельный справочник и nullable FK после расширения объёма.
3. DATA-04 требует отдельного аудита всех переходов. Здесь сохранены авторы и время двух разрешённых переходов, но отдельного журнала нет. Смена исполнителя, редактирование заявки, повторное открытие не разрешены; расширение процесса потребует журнала и новых правил.
4. DATA-07 и GWT-03 требуют журнал идемпотентных операций. Его нет: PK истории защищает повтор завершения, но не повтор INSERT оборудования/заявки и не хранит результат операции. Нужна отдельная таблица и транзакционный протокол.
5. DATA-01 предлагает версию Equipment, но текущая модель её не имеет. Она отложена до проектирования редактирования; версия заявки уже сохранена. DATA-05 предлагает отдельный ID истории; здесь осознанно выбран текущий `FaultId` как PK, поскольку история создаётся только из заявки.
6. Длины, допустимые символы, сроки хранения, окончательная Unicode-нормализация, управление ролями и политика удаления персональных данных требуют согласования. Статусы оборудования согласованы с текущим единым AllowedStatuses, а не устаревшим замечанием user_stories о различии валидатора и тестовых данных.

## Проверка и её пределы

Выполнена статическая логическая проверка: порядок создания зависимостей; типы PK/FK и соответствие `int`/`Guid`; NOT NULL/CHECK; три допустимых состояния заявки; оба перехода; невозможность пропуска/возврата; связь истории с тем же оборудованием; одна история на заявку; атомарный откат при ошибке триггера; запрет каскадного удаления; согласованность имён индексов и столбцов. C# не менялся, поэтому сборка приложения не проверяет этот SQL и не использовалась как доказательство его корректности.

**SQL не запускался на PostgreSQL/Supabase.** `psql` не найден в PATH; подключение к БД не выполнялось. Синтаксис, срабатывание триггеров, collation, RLS и планы запросов не подтверждены исполнением.

После разрешения на отдельную тестовую БД необходимо проверить: применение целиком; дубли номера с регистром/Unicode-пробелами; пустые поля/неизвестные статусы; отсутствующие FK; переходы и авторов; неполное завершение; искусственную ошибку INSERT истории с полным откатом; несовпадающее оборудование/снимок истории; запрет изменения истории; удаление связанных объектов; параллельные INSERT номера и UPDATE с одинаковой ожидаемой версией; отсутствие доступа anon/authenticated. Отдельно проверить положительный сценарий с двумя реальными Auth-пользователями и повторным чтением UTC-дат.

Официальные источники: [Supabase: пользовательские данные и ссылки на auth.users](https://supabase.com/docs/guides/auth/managing-user-data), [PostgreSQL: pg_trgm и индексы LIKE/ILIKE](https://www.postgresql.org/docs/17/pgtrgm.html). Они использованы для проверки решения Auth и предложения по подстрочному поиску, а не как свидетельство выполнения SQL.
