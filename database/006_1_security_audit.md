# Дополнительный аудит этапа 6.1 для PostgreSQL 17

## Заключение

Миграция готова **к первой контролируемой проверке на отдельном тестовом стенде**, после просмотра предварительной диагностики. Она не объявляется готовой к production. В этом аудите SQL не выполнялся ни в Supabase, ни локально; роль и пароль не создавались. Синтаксис и семантика сверены с документацией PostgreSQL 17 и существующими исходниками, но серверный разбор и выполнение ещё не подтверждены.

Обновление от 17.10.2026: пользователь передал реальную диагностику public.rls_auto_enable() и согласовал сохранение её ACL. В завершающую проверку миграции добавлено одно адресное исключение с MD5 `846ec2fbff751d24b890656d63c3a9bf`, владельцем postgres, точным search_path и проверками OID/типа/событийной привязки/тегов. Полный актуальный протокол и остаточные риски: [006_1_rls_auto_enable_audit.md](006_1_rls_auto_enable_audit.md). REVOKE не выполнять. Остальные части миграции и все остальные проверки сохранены; исключение не выдаёт прав. Последующие описания исходных проверок читаются с учётом этого единственного изменения.

## 1. SECURITY DEFINER: диагностика до CREATE ROLE

В SQL Editor вручную выполнить **только** [006_1_equipment_api_diagnostics.sql](006_1_equipment_api_diagnostics.sql). Этот файл содержит SELECT, не создаёт роль и не вызывает проверяемые функции. Имена, сигнатуры, владельцы и расширения — метаданные; тела функций, пароли, JWT и конфигурация с секретами не выводятся.

В SQL Editor выделять и выполнять каждый SELECT/CTE-блок отдельно, чтобы результат последнего SELECT не скрыл список функций. Ключевой блок начинается с `WITH target AS` и заканчивается `ORDER BY nspname, proname, identity_arguments;`. При отсутствующей equipment_api последний блок прав ожидаемо возвращает 0 строк — это не результат проверки SECURITY DEFINER.

Главный SELECT работает и до существования equipment_api:

- Эффективный EXECUTE будущей роли на существующие функции приходит из PUBLIC; у новой роли ещё нет прямых grants и членства в других ролях.
- Эффективный USAGE схемы — PUBLIC USAGE либо запланированный GRANT USAGE public.
- Для NULL ACL используется acldefault: NULL proacl не означает отсутствие PUBLIC EXECUTE.
- После создания роли расчёт использует has_schema_privilege/has_function_privilege по её OID.
- Результат перечисляет ровно доступные SECURITY DEFINER-кандидаты за пределами pg_catalog/information_schema, соответствующие условию завершающей проверки миграции. Присутствие extension_name лишь помогает аудиту, а не разрешает функцию автоматически.

Это прогноз по текущим каталогам. Изменения расширений, grants, событийных триггеров и схем между диагностикой и миграцией могут изменить результат; завершающая проверка миграции остаётся обязательной.

Непустой результат означает эффективное ACL-право EXECUTE, но не доказывает успешный обычный вызов: PL/pgSQL event_trigger требует специального контекста. Даже штатная функция может предоставлять нежелательный сетевой доступ, DDL или доступ к данным. Исключать целиком auth, extensions, storage или любую другую схему нельзя. Единственное согласованное исключение — точное совпадение rls_auto_enable по актуальному протоколу; её строка остаётся видна в общей диагностике.

Если результат непустой:

1. Остановить подготовку production-развёртывания и отдельно разобрать точную сигнатуру, владельца, версию расширения, реализацию и транзитивные вызовы каждой функции, её search_path и фактическое действие.
2. Не запускать функцию ради проверки и не отзывать глобальные PUBLIC-права Supabase автоматически.
3. Только после доказательства безопасности возможна отдельная согласованная точечная правка: точная schema-qualified signature, ожидаемый владелец, подтверждённая принадлежность/версия расширения при наличии и проверка неизменности определения. Совпадения имени или принадлежности расширению недостаточно. Такую правку нельзя обосновать без фактического списка кандидатов.

Таким образом, миграция может штатно остановиться на Supabase SECURITY DEFINER-функции. Это предусмотренный отказ до проверки конкретного окружения, а не повод убрать защиту.

## 2. Транзакционный контекст

Обязательная последовательность на **одном** соединении Npgsql:

```text
проверка JWT → Guid из проверенного sub → BEGIN
→ параметризованный set_config(..., true)
→ SQL-операция на той же транзакции
→ COMMIT при успехе / ROLLBACK при ошибке или отмене
→ Dispose и возврат соединения в пул
```

SQL-команда установки:

```sql
SELECT set_config('equipment.user_id', $1, true);
```

В будущем C#-адаптере $1 задаётся параметром из проверенного ClaimsPrincipal. В SQL Editor голый $1 не исполняется как готовая команда без binding; в read-only тесте используется PREPARE/EXECUTE. Вне явного BEGIN локальная настройка закончится вместе с командой и не дойдёт до следующей SQL-операции.

Политики оборудования принимают списки допустимых ролей как константы, а реальные полномочия читают из public.profiles.roles/is_active. Политика profiles сопоставляет id с current_profile_id, не обращаясь к has_any_role; рекурсии нет. Ни user_metadata, ни app_metadata, ни request.jwt.claims, ни HTTP DTO не используются в этих политиках.

Однако **сам GUC не доказывает происхождение UUID**. PostgreSQL не видит валидатор JWT и не способен отличить проверенный sub от UUID, установленного владельцем database credentials. Корректный параметризованный запрос предотвращает SQL injection в значении, но не доказывает личность пользователя. Ключевое обязательство будущего адаптера — никогда не брать этот UUID из HTTP-тела/URL/непроверенного токена. Нынешний C# такой адаптер ещё не реализует; миграция не включает его автоматически.

Защита от переноса контекста:

- is_local=true всегда, включая SELECT и повтор после транзакционного retry;
- запрещены session-level SET, set_config(..., false) и контекст в Options;
- каждый запрос устанавливает контекст заново до чтения данных;
- соединение/транзакция не разделяются параллельными пользователями;
- при rollback до savepoint, предшествующего установке, контекст установить заново либо закончить транзакцию;
- No Reset On Close=false, без обхода стандартного сброса Npgsql;
- после исключения/отмены транзакция завершается до возврата соединения в пул.

SET LOCAL после завершения восстанавливает предыдущее session-level значение, если кто-то установил его раньше. Поэтому одного SET LOCAL недостаточно для защиты от ошибочного session-level SET: общий адаптер и тесты обязательны. RLS не защищает от компрометированного сервера/login с произвольным SQL.

## 3. PostgreSQL 17, права и Supabase

| Предмет | Результат статического аудита |
| --- | --- |
| DDL | BEGIN/COMMIT, CREATE ROLE/SCHEMA/FUNCTION/POLICY и column GRANT соответствуют PostgreSQL 17; повторная установка отклоняется |
| pg_auth_members | admin_option, inherit_option, set_option существуют в 17; проверяется направление membership, а не только NOINHERIT |
| ADMIN создателя | Разрешён только creator с ADMIN TRUE, INHERIT FALSE, SET FALSE; иной createrole_self_grant может намеренно остановить установку |
| Административные флаги | CREATE ROLE явно использует NOSUPERUSER/NOCREATEDB/NOCREATEROLE/NOREPLICATION/NOBYPASSRLS |
| Helpers | Две STABLE SECURITY INVOKER-функции, search_path=pg_catalog, schema-qualified ссылки, PUBLIC EXECUTE отозван |
| Права функции CHECK | EXECUTE trim_whitespace выдан новой роли; генерация normalized_inventory_number не требует выдачи INSERT/UPDATE этого столбца |
| SELECT | Табличный SELECT equipment и column SELECT id/roles/is_active профиля; RLS собственного активного профиля ограничивает helper |
| INSERT/UPDATE | Только четыре редактируемых столбца; нет изменения id или generated-столбца; INSERT WITH CHECK, UPDATE USING и WITH CHECK |
| DELETE | Только equipment при активном engineer; связанные записи защищает FK RESTRICT независимо от видимости faults |
| Последовательность | Только USAGE equipment_id_seq; SELECT/UPDATE и доступ к другим последовательностям отклоняются проверкой |
| UNIQUE/FK | Существующие ограничения не изменяются; 23505 для дубликата и 23503 для связанного удаления остаются ожидаемыми |
| INVOKER-триггеры | Исходные включённые trigger-функции проверяются, не переписываются; оборудование не имеет неожиданных пользовательских триггеров по preflight |
| Заявки/история | У новой роли нет этих прав; завершение и создание истории не включаются этапом 6.1 |
| Старые политики | Политики именованных authenticated/equipment_app не применяются к новой роли без membership; PUBLIC-политики останавливают миграцию |
| equipment_app | Её роли, grants, политика и чтение профилей не меняются |

Политики не отменяют ACL. Например, manager может иметь технический column UPDATE через общий login, но RLS не допускает строк для изменения. Нулевой UPDATE/DELETE не является явным HTTP 403; API обязан сохранить собственную проверку профиля.

SQL Editor Supabase выполняет административный SQL, но не превращает его в доказательство RLS обычного login. Исполнитель миграции должен иметь CREATEROLE либо соответствующие административные права, CREATE базы для новой схемы, права владельца таблиц для CREATE POLICY и право выдавать grants функций/таблиц/последовательности. Первый и третий SELECT диагностического файла показывают исходные данные для этой проверки; все транзитивные административные возможности автоматически ими не доказываются.

Supabase использует управляемого администратора, поэтому нельзя обещать выполнение только на основании синтаксиса. Event triggers, default privileges, дополнительные функции и PUBLIC ACL проверяются на конкретном тестовом проекте. При отказе вся миграция откатывается; не выдавать equipment_api административные права ради успешной установки.

## 4. Безопасные тесты

После ручной миграции на тестовом стенде использовать [006_1_equipment_api_rls_readonly.psql](006_1_equipment_api_rls_readonly.psql) под настоящим login equipment_api с VerifyFull. Файл содержит команды клиента psql, поэтому не вставлять его целиком в SQL Editor. Он запрашивает UUID двух **уже существующих** тестовых профилей: активного engineer и manager/maintenance_specialist без engineer. Профили/пользователей файл не создаёт.

Из корня репозитория в уже открытой соответствующей psql-сессии:

```psql
\i database/006_1_equipment_api_rls_readonly.psql
```

Файл использует только read-only транзакции: SELECT, DO с проверками и установку локальных параметров. Он не содержит INSERT/UPDATE/DELETE/nextval и не потребляет identity-значения. Большинство транзакций заканчивается ROLLBACK; одна read-only транзакция заканчивается COMMIT специально для проверки сброса после COMMIT. PREPARE/DEALLOCATE меняют только состояние сессии. При первой ошибке psql останавливает файл; вручную выполнить ROLLBACK и закрыть диагностическую сессию, чтобы не оставлять транзакцию/подготовленную команду.

Проверяются: RLS без контекста, собственный профиль инженера, чтение, отсутствие присвоения engineer через фиктивные метаданные, сброс после COMMIT/ROLLBACK, пустой и неверный UUID. Последние SELECT должны вернуть true для запрета мутаций profiles и ожидаемых sequence ACL. Ошибки бизнес-проверок завершают сценарий исключением. UUID и Auth-токены не выводятся; count оборудования — данные, видимые соответствующему авторизованному профилю.

Это проверка SELECT RLS и условий политик/ACL, **не фактический тест разрешённого/запрещённого INSERT/UPDATE/DELETE**. Полные DML-проверки выполняются только на отдельном тестовом проекте. Ниже необязательный ручной пример: под equipment_api в psql, после проверки отсутствия неожиданных триггеров, с UUID тестового инженера в переменной engineer_id:

```psql
\set ON_ERROR_STOP on
BEGIN;
PREPARE em_dml_context(text) AS
    SELECT set_config('equipment.user_id', $1, true) IS NOT NULL AS context_set;
EXECUTE em_dml_context(:'engineer_id');
INSERT INTO public.equipment (name, inventory_number, location, status)
VALUES ('RLS audit fixture', 'AUDIT-' || gen_random_uuid()::text, 'Test stand', 'Исправно')
RETURNING id AS fixture_id \gset audit_
UPDATE public.equipment SET location = 'Test stand updated' WHERE id = :audit_fixture_id;
DELETE FROM public.equipment WHERE id = :audit_fixture_id;
ROLLBACK;
DEALLOCATE em_dml_context;
\unset audit_fixture_id
```

Проверить один созданный ID, UPDATE 1 и DELETE 1. Любую ошибку завершить явным ROLLBACK, не COMMIT. UUID engineer_id задаётся администратором только для теста. **Не выполнять этот DML-пример на production:** nextval identity не откатывается, даже если строки откатываются. ROLLBACK также не гарантирует отмену посторонних внешних действий неожиданного триггера. Реальные UNIQUE/FK, отрицательные DML и атомарность будущего завершения заявок проверяются на изолированных фикстурах следующего интеграционного этапа.

Read-only файл выполняет несколько транзакций в одной сессии, но не тестирует Npgsql pool. Для будущего автоматического интеграционного теста задать отдельный пул MaxPoolSize=1, No Reset On Close=false: engineer/COMMIT → повторное получение соединения/без контекста → reader/ROLLBACK → повторное получение/без контекста. Повторить после исключения и cancellation, проверять отсутствие видимых строк/старого current_profile_id до установки нового контекста. Только после этого разрешать рабочее переключение адаптера.

## Результаты и ограничения этого аудита

В исходном этапе исключений не было; после диагностики пользователя от 17.10.2026 внесено одно адресное исключение rls_auto_enable только в проверку доступных SECURITY DEFINER. RLS, реальные права PostgreSQL и бизнес-логика не изменялись. Ни один подготовленный runtime-тест не объявляется пройденным. SQL-парсер PostgreSQL и серверная PL/pgSQL-проверка не запускались. Build/test C# не запускались: приложение этой правкой не менялось.

Выполненные структурные проверки файлов: баланс круглых скобок соблюдён в миграции, диагностике и read-only сценарии; dollar-delimiters парные. В диагностике нет изменяющих команд. В read-only сценарии нет DML/nextval: 8 READ ONLY-транзакций, 7 ROLLBACK и один COMMIT без изменений данных. git diff --check завершился кодом 0 с прежним предупреждением LF/CRLF для ранее изменённого Services/FaultDataService.cs; этот C#-файл не редактировался. Это проверки структуры текста, не серверный SQL-парсинг.

Источники для сверки: [pg_auth_members PostgreSQL 17](https://www.postgresql.org/docs/17/catalog-pg-auth-members.html), [ACL и privilege functions](https://www.postgresql.org/docs/17/functions-info.html), [set_config](https://www.postgresql.org/docs/17/functions-admin.html), [RLS](https://www.postgresql.org/docs/17/ddl-rowsecurity.html), [Npgsql: сброс состояния пула](https://www.npgsql.org/doc/performance.html).
