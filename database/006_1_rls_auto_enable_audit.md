# rls_auto_enable: аудит перед этапом 6.1

## Принятое решение от 17.10.2026 — актуальный порядок

Пользователь завершил диагностику в реальной Supabase PostgreSQL 17 и передал: MD5 определения `846ec2fbff751d24b890656d63c3a9bf`, владелец postgres, SECURITY DEFINER, `search_path=pg_catalog`, PUBLIC EXECUTE, привязка ensure_rls с `evtenabled=O` и тегами CREATE TABLE / CREATE TABLE AS / SELECT INTO. Ранее также сообщено отсутствие extension membership. Это результаты пользователя; агент не выполнял диагностику повторно и полного тела функции в сообщении не получил.

**Согласовано сохранить инфраструктурную функцию и её ACL. REVOKE не выполнять.** Файл `006_1_rls_auto_enable_revoke.sql` оставлен только как исторический отклонённый вариант, не является предварительным шагом миграции. Все разделы ниже, обсуждающие REVOKE или неподставленный MD5, описывают предыдущий этап и не являются текущей инструкцией.

В `006_1_equipment_api_security.sql` теперь внесено одно исключение только в последнюю проверку доступных SECURITY DEFINER-функций. Проверяются:

- OID, разрешённый через точную сигнатуру `to_regprocedure('public.rls_auto_enable()')`, схема и имя; числовой OID не переносится между проектами.
- postgres как владелец функции, PL/pgSQL, ноль аргументов, тип результата event_trigger, SECURITY DEFINER через исходное внешнее условие.
- Точное равенство proconfig массиву `search_path=pg_catalog` и точное совпадение переданного MD5 всего `pg_get_functiondef`.
- Отсутствие членства функции в расширении.
- ensure_rls с тем же evtfoid, владельцем postgres, событием ddl_command_end и строго `evtenabled='O'`.
- Ровно три тега, оба включения массивов: CREATE TABLE / CREATE TABLE AS / SELECT INTO, без дополнительных тегов. Порядок тегов не важен.
- Отсутствие других event triggers, ссылающихся на функцию.

`AND NOT coalesce((...), false)` исключает только совпавший объект: NULL или любое несовпадение сохраняет блокировку доступной функции. Более строгие условия типа/языка, события, владельца event trigger и отсутствия дополнительных привязок проверяются непосредственно при будущем запуске; не все эти поля были заново приведены в последнем сообщении. Несовпадения нельзя исправлять автоматическим ослаблением условия.

### Текущая инструкция проверки

1. Перед будущим ручным развёртыванием повторить оба SELECT-файла диагностики, сохранив определение и ACL. В адресной диагностике сверить все перечисленные условия. Исходный общий SELECT продолжит показывать эту функцию и `would_block_migration=true`: это сырой сигнал доступности до адресного исключения, а не итог обновлённого предиката миграции. Не требовать исчезновения строки и не отзывать права ради пустого результата.
2. На отдельном тестовом проекте проверить установку основной миграции целиком. Любая другая доступная SECURITY DEFINER-функция должна вызывать отказ и полный откат. Проверить отрицательные варианты точного предиката: другой MD5, владелец, proconfig, тип результата, evtfoid, выключенный/иной режим триггера, другой тег или дополнительная привязка — совпадения быть не должно. Менять инфраструктуру production для теста нельзя; для тестирования сравнения использовать изолированные фикстуры/копию стенда.
3. После установки сравнить ACL, MD5, владельца и настройки rls_auto_enable/ensure_rls с исходным снимком. Они должны остаться прежними. `has_function_privilege('equipment_api', 'public.rls_auto_enable()', 'EXECUTE')` ожидаемо true через PUBLIC; считать false целью этого решения нельзя. Проверить также отсутствие CREATE, владения, лишнего членства, BYPASSRLS и SUPERUSER у equipment_api.
4. Сохранить все прежние проверки таблиц, столбцов, последовательностей, политик и контекста пользователя. Положительные/отрицательные RLS-проверки выполнять по основной инструкции. Автоматическое включение RLS на новой public-таблице проверять только доверенной DDL-ролью на отдельном стенде; три CREATE-тега описаны ниже, но шаг REVOKE из старого сценария пропустить.

### Принятые остаточные риски

PUBLIC EXECUTE и USAGE public технически доступны equipment_api. Исключение изменяет только результат аудита, не является ограничением доступа. Для проверяемого варианта PL/pgSQL с результатом event_trigger PostgreSQL 17 отвергает обычный SELECT вне контекста event trigger; ACL true не доказывает успешный прямой вызов. Runtime-тест этого поведения в текущем этапе не выполнялся.

Если иной механизм/будущая реализация допустит обычный вызов, код выполнится с правами postgres: возможный ущерб определяется телом и его зависимостями, потенциально включая привилегированные DDL и обход прикладных ограничений. Нельзя считать такую функцию безопасной только по имени. Отсутствие CREATE у equipment_api ограничивает создание таблиц, но не заменяет аудит доступных посредников и способов запуска DDL. Нельзя публиковать универсальный SQL/RPC-прокси и передавать credentials роли клиенту.

MD5 фиксирует именно предоставленное определение, а не доказывает безопасность кода; его надёжность не рассчитана на злонамеренную подмену. Проверка однократна: последующие изменения функции, зависимостей, trigger-настроек, ACL или членства не отзывают существующие права автоматически. Изменение после миграции требует повторного аудита. Supabase-обновление может изменить определение и заблокировать будущую повторную подготовку; новый хеш нельзя принимать автоматически. Отклонённый вариант REVOKE не применять без нового решения пользователя.

### Протокол текущей локальной правки

В SQL изменён только комментарий и предикат одной завершающей проверки. Остальные части миграции проверены сравнением SHA-256 неизменных префикса и суффикса с локальным снимком до правки. Существующие CREATE ROLE/GRANT/POLICY не добавлялись и не менялись; новые GRANT/REVOKE отсутствуют. SQL в Supabase и локальном PostgreSQL не выполнялся, C# не изменялся, commit/push не выполнялись. Серверный парсинг и runtime-проверки ещё предстоят.

## История предыдущего этапа (не инструкция к выполнению)

## Вывод и граница доказательств

По переданному результату действительно имеется SECURITY DEFINER-функция `public.rls_auto_enable()` владельца `postgres`, без членства в расширении, с PUBLIC EXECUTE. Для новой equipment_api доступ через PUBLIC объясняет отказ строгой проверки миграции. NOINHERIT не исключает PUBLIC. Отдельный `REVOKE ... FROM equipment_api` не перекроет право PUBLIC.

Имя совпадает с официальным примером Supabase автоматического RLS: PL/pgSQL-функция без аргументов с результатом `event_trigger`, безопасным search_path, вызовом `pg_event_trigger_ddl_commands()` и `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`; её вызывает `ensure_rls` на `ddl_command_end` для CREATE TABLE / CREATE TABLE AS / SELECT INTO. Это сильное указание на назначение, **но приведённый SELECT не подтверждает фактическое тело и наличие включённого event trigger**. Владелец postgres и extension_name=NULL не доказывают ни пользовательское, ни инфраструктурное происхождение: функция могла быть создана настройкой, инструментом, SQL Editor или миграцией. В Supabase postgres управляет event triggers через Supautils.

В этом этапе к Supabase не подключались, каталоги удалённой БД не читались. Поэтому фактическая привязка, дополнительные grants и возможное инфраструктурное использование остаются непроверенными. Вместо выдуманного результата подготовлена адресная диагностика.

## Требуется ли PUBLIC EXECUTE

Для вызова **существующим event trigger** в PostgreSQL 17 PUBLIC EXECUTE не требуется. В `EventTriggerInvoke` движок получает функцию через `fmgr_info` и вызывает её с контекстом EventTriggerData через `FunctionCallInvoke`, без проверки EXECUTE роли, инициировавшей DDL. SECURITY DEFINER продолжает выполнять тело с правами владельца. Поэтому узкий REVOKE PUBLIC не удаляет/не отключает event trigger и не меняет его контекст исполнения. Владелец сохраняет собственные права.

Результат `has_function_privilege = true` означает ACL-доступ, но сам по себе не означает вызываемый обычным SELECT/RPC endpoint: PL/pgSQL-функция с return type event_trigger требует контекста event trigger. При прямом вызове PostgreSQL отвергает её как event trigger function вне этого контекста. Это не повод исключить все DEFINER-функции или вообще все функции типа event_trigger: необходимо проверить конкретный объект, его тело и способы запуска.

Вывод: после подтверждения указанной реализации и отсутствия другого необходимого использования PUBLIC EXECUTE его отзыв безопасен **для самого механизма автоматического RLS**. Без тела и зависимостей нельзя заявить безопасность для всей инфраструктуры проекта. Каталожные зависимости не находят все ссылки в строках PL/pgSQL, динамическом SQL, внешних deploy-скриптах или dashboard-коде; их проверяют дополнительно в истории миграций и используемых инструментах.

## Подготовленное точечное исправление

Предпочтительный путь — [006_1_rls_auto_enable_revoke.sql](006_1_rls_auto_enable_revoke.sql), отдельный предшествующий шаг:

```sql
REVOKE EXECUTE ON FUNCTION public.rls_auto_enable() FROM PUBLIC;
```

Файл пока намеренно блокируется `reviewedDefinitionMd5 = NULL`. После просмотра реального тела и зависимостей администратор фиксирует MD5 определения из диагностики в локальной копии. Автоматически получать и тут же «доверять» этому хешу нельзя. MD5 служит индикатором изменения просмотренного текста, а не защитой от администратора-злоумышленника. Дополнительные guards проверяют владельца, язык, return type, search_path, отсутствие extension membership и точную привязку включённого ensure_rls. Несовпадение приводит к откату; функция не заменяется.

Изменение разрешений происходит только при будущем ручном исполнении файла, которое сейчас не выполнялось. Скрипт отзывает только PUBLIC EXECUTE у одной функции, не меняет действующие роли, другие grants, default privileges и RLS. При прямом/групповом EXECUTE equipment_api отдельная проверка отклоняет шаг — лишние права не отзываются молча. Если роли ещё нет, её создаст исходная 006_1, чья строгая проверка останется окончательным контролем эффективных прав.

В `006_1_equipment_api_security.sql` изменён только поясняющий комментарий у проверки. Все SECURITY DEFINER-функции по-прежнему проверяются; allowlist не добавлен. Создание новой роли и выдача ей прав выполняются только будущим отдельным запуском основной миграции, не этим исправлением.

## Если изменение инфраструктурного ACL запрещено

Не обходить отказ автоматически. Минимальная альтернатива — изменить только предикат проверки основной миграции, добавив к условию доступной DEFINER-функции `AND NOT (...)` для **одного изученного объекта**. Остальные GRANT и политики остаются прежними. Шаблон исключения ниже сейчас НЕ внесён в исполняемую миграцию; NULL обязательно заменить вручную на хеш просмотренного определения. Пока NULL, исключение не действует благодаря COALESCE:

```sql
AND NOT coalesce((
    p.oid = pg_catalog.to_regprocedure('public.rls_auto_enable()')
    AND n.nspname = 'public' AND p.proname = 'rls_auto_enable'
    AND p.prokind = 'f' AND p.pronargs = 0
    AND p.prorettype = 'pg_catalog.event_trigger'::regtype
    AND p.proowner = 'postgres'::regrole
    AND p.prolang = (SELECT oid FROM pg_catalog.pg_language WHERE lanname = 'plpgsql')
    AND p.proconfig @> ARRAY['search_path=pg_catalog']
    AND pg_catalog.md5(pg_catalog.pg_get_functiondef(p.oid)) = NULL::text -- просмотренный MD5
    AND NOT EXISTS (
        SELECT 1 FROM pg_catalog.pg_depend d
        WHERE d.classid = 'pg_catalog.pg_proc'::regclass AND d.objid = p.oid
          AND d.refclassid = 'pg_catalog.pg_extension'::regclass AND d.deptype = 'e')
    AND EXISTS (
        SELECT 1 FROM pg_catalog.pg_event_trigger e
        WHERE e.evtfoid = p.oid AND e.evtname = 'ensure_rls'
          AND e.evtowner = 'postgres'::regrole
          AND e.evtevent = 'ddl_command_end' AND e.evtenabled IN ('O', 'A')
          AND e.evttags @> ARRAY['CREATE TABLE', 'CREATE TABLE AS', 'SELECT INTO']::text[]
          AND e.evttags <@ ARRAY['CREATE TABLE', 'CREATE TABLE AS', 'SELECT INTO']::text[])
    AND NOT EXISTS (
        SELECT 1 FROM pg_catalog.pg_event_trigger e
        WHERE e.evtfoid = p.oid AND e.evtname <> 'ensure_rls')
    AND NOT EXISTS (
        SELECT 1 FROM pg_catalog.pg_namespace s
        WHERE s.nspname !~ '^pg_' AND s.nspname <> 'information_schema'
          AND pg_catalog.has_schema_privilege('equipment_api', s.oid, 'CREATE'))
), false)
```

Применять этот вариант можно только после аудита тела: оно должно действовать исключительно в рассмотренном DDL-контексте и не давать дополнительных операций equipment_api. Проверка отсутствия CREATE уже есть выше в основной миграции; она повторена в шаблоне для ясной границы исключения. Не давать роли CREATE/членство/владение/event-trigger-права ради прохождения проверки. Само исключение не добавляет GRANT, однако **унаследованное PUBLIC EXECUTE остаётся** — это принятие узкого проверенного ACL-сигнала, а не устранение права. Если требование означает буквально отсутствие effective EXECUTE, такой вариант не подходит: при PUBLIC EXECUTE невозможно индивидуально запретить его одной роли, в PostgreSQL нет DENY. Тогда требуется согласованное изменение ACL или изоляция; проверка должна продолжать отклонять миграцию.

Имя, владелец, return type или extension_name по отдельности недостаточны. Нельзя использовать `NOT p.prosecdef`, исключать весь public, все event_trigger или все объекты владельца postgres. Изменение тела/владельца/привязки после проверки требует повторного аудита: одноразовая миграционная проверка не заменяет постоянный контроль.

## Инструкция проверки (только будущие ручные действия)

1. Выполнить [006_1_rls_auto_enable_diagnostics.sql](006_1_rls_auto_enable_diagnostics.sql) владельцем в SQL Editor. Это только SELECT; функцию не вызывает. Сохранить тело, MD5, ACL, зависимости и параметры event trigger. Отсутствие функции/триггера либо другой тип/теги — остановка, не автоматическое исправление.
2. Проверить, что тело включает RLS только для новых таблиц целевой схемы; проверить обработчик ошибок: варианты с подавлением исключений могут оставлять таблицу без RLS. Эта работа не исправляет тело инфраструктурной функции. Проверить исходные grants и используемые deployment-инструменты. `pg_depend` и текстовый поиск — вспомогательные, не исчерпывающие доказательства.
3. На отдельном тестовом проекте с тем же определением/триггером и ACL зафиксировать исходное поведение CREATE TABLE, CREATE TABLE AS и SELECT INTO **обычных таблиц public**, затем применить рассмотренный REVOKE и повторить тем же DDL-пользователем. TEMP-таблица не подходит: функция обычно пропускает pg_temp. Выполнять DDL только после аудита остальных event triggers: ROLLBACK не гарантирует отмену внешних действий.
4. В тестовой транзакции создавать таблицу со случайным уникальным именем без `IF NOT EXISTS` и без явного ENABLE RLS; сразу проверять `pg_class.relrowsecurity = true`, затем ROLLBACK. Повторить для всех трёх CREATE-тегов. Пример для одного тега под доверенным DDL-пользователем:

```sql
BEGIN;
CREATE TABLE public.em_rls_probe_reviewed_0061 (id integer);
SELECT oid::regclass AS table_name, relrowsecurity
FROM pg_catalog.pg_class
WHERE oid = 'public.em_rls_probe_reviewed_0061'::regclass;
ROLLBACK;
```

Имя примера сначала заменить на свободное. Для остальных вариантов использовать `CREATE TABLE public.<свободное_имя> AS SELECT 1 AS id` и `SELECT 1 AS id INTO public.<свободное_имя>` в отдельных откатываемых транзакциях. Ошибка завершает проверку с ROLLBACK. Не проверять DDL под equipment_api: ей CREATE не положен.

5. После отзыва повторить оба диагностических файла — адресный и исходный `006_1_equipment_api_diagnostics.sql`. Ожидать отсутствие PUBLIC EXECUTE, неизменные definition_md5, owner, event trigger, теги и включённость; сохранённое право владельца. Прямые права anon/authenticated/service_role могут остаться из прежних ACL — не отзывать их автоматически и не объявлять effective_execute=false без результата. До создания equipment_api исходная диагностика моделирует PUBLIC, а не фактический login.
6. Только после отдельного разрешения на развёртывание основной миграции проверить фактический `has_function_privilege('equipment_api', 'public.rls_auto_enable()', 'EXECUTE') = false` для варианта REVOKE, отсутствие CREATE и лишнего членства; строгая проверка всех прочих DEFINER должна пройти без исключений. Если PUBLIC сохранили через согласованный fallback, ACL EXECUTE останется true и должен быть явно отражён в протоколе, а не назван отсутствующим правом.
7. Негативный тест проверки на изолированном стенде: другая доступная SECURITY DEFINER-функция должна по-прежнему блокировать миграцию; изменение определения разрешённого объекта должно блокировать fallback. Не создавать такие функции в production.

SQL здесь не выполнялся и не проверялся серверным парсером. Выполнен статический анализ подготовленных файлов; C# не менялся, build/test не запускались, поскольку они не проверяют ACL/event triggers PostgreSQL. Действующие роли, RLS и облачные объекты не изменены; commit/push отсутствуют.
