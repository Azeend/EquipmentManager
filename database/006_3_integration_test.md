# Один сквозной тест PostgreSQL-хранилищ

Тест: `PostgresStoresIntegrationTests.EquipmentFaultMaintenance_PersistsAcrossConnections_AndEnforcesRoles` в проекте EquipmentManager.Tests. По умолчанию **пропущен**: обычный запуск тестов не обращается к Supabase. В рамках подготовки он не запускался; проверяется только сборка.

## Что нужно подготовить до запуска

Только в уже существующем **EquipmentManager-Test**, где установлены 006_1 и 006_3:

| Настройка | Назначение |
| --- | --- |
| Project Ref тестового проекта | Сверить в Dashboard именно EquipmentManager-Test; имя проекта само по себе недостаточно |
| Подключение `equipment_api` | Парольный прямой вход ограниченной DB-роли, без SET ROLE, база postgres, SSL Mode=VerifyFull |
| Отдельное подключение `postgres` того же Test project | Только предварительная проверка возможности очистки и точная очистка в finally; в положительном/отрицательном сценарии CRUD не используется |
| UUID тестового engineer | Существующий Auth-пользователь и активный профиль с **единственной** ролью engineer |
| UUID тестового maintenance_specialist | Другой Auth-пользователь и активный профиль с **единственной** ролью maintenance_specialist |
| UUID тестового manager | Третий Auth-пользователь и активный профиль с **единственной** ролью manager |

Использовать только выделенные тестовые аккаунты Test project, не UUID пользователей основной базы. Тест не создаёт/не меняет Auth-пользователей и профили; если они отсутствуют, их должен заранее подготовить администратор тестового проекта. Пароли пользователей Auth, JWT, publishable/service_role keys тесту не нужны. Это интеграция хранилищ: доверенный серверный principal моделируется по явно заданным тестовым UUID, а JWT/cookie-проверка покрывается существующими отдельными тестами.

Поддерживаются прямой host `db.<TEST_REF>.supabase.co` с Username=equipment_api/postgres либо **session pooler**, порт 5432, host из Dashboard с окончанием `.pooler.supabase.com`, Username=equipment_api.<TEST_REF>/postgres.<TEST_REF>. Transaction pooler на порту 6543 не допускается. Pooling принудительно выключен: после уничтожения первого executor создаются новые подключения, и данные читаются после реальных COMMIT.

Оба подключения жёстко сопоставляются с одним явно указанным Test Ref. Основной Project Ref из текущего appsettings.json (`cyzanurmyswswbicjiaf`, публичный идентификатор) дополнительно запрещён в тесте. Пароли/строки подключения не выводятся, исходные исключения заменяются безопасным сообщением с этапом и типом ошибки. Нельзя включать внешнее журналирование параметров/секретов в test runner/APM. Не использовать скриншоты с переменными окружения или debugger Locals в отчёте.

## Почему нужно отдельное разрешение на очистку

Хранилища коммитят каждую операцию. Общая откатываемая транзакция не проверила бы сохранность через независимое подключение. При этом equipment_api не имеет DELETE на faults/history, а guard истории запрещает DELETE даже владельцу. Выдавать equipment_api дополнительные права или ослаблять рабочие guards ради теста нельзя.

В `finally` используется **отдельный Test-only owner connection**: одна транзакция блокирует equipment/faults/history в ACCESS EXCLUSIVE, проверяет уникальную метку и авторов, отключает только `maintenance_records_guard`, удаляет историю → заявку → оборудование только своего запуска и включает guard **до COMMIT**. RLS не отключается; роли, функции и миграции не меняются. При сбое до COMMIT откатываются и удаления, и изменение состояния guard. Блокировки не позволяют другим транзакциям работать с временно отключённым guard; запускать в спокойном тестовом проекте без параллельной работы (очистка кратко блокирует три таблицы).

Явное `EM_PG_TEST_ALLOW_CLEANUP=EquipmentManager-Test only` подтверждает именно этот механизм. До первой записи проверяются оба login, владельцы таблиц, состояние guard и три профиля. Без исправного cleanup-подключения тест не должен начинать запись. Ни один CRUD сценария не выполняется через postgres.

Для фикстуры генерируется криптографически уникальная метка `LAB5-E2E-<Guid>` в Name, InventoryNumber и описании заявки. Очистка проверяет место установки и UUID авторов/исполнителей; при неожиданной чужой связи прекращается до изменения guard. Нет TRUNCATE, DELETE всех строк, CASCADE, сброса sequence или массового удаления по префиксу. Отрицательные прямые SQL-проверки всегда откатываются, даже при неожиданном разрешении операции.

Перед первой записью создаётся `%TEMP%\EquipmentManager-PgIntegration\<метка>.json`: только метка, Test Ref и тестовые UUID, без паролей/токенов/строк подключения. При штатной очистке файл удаляется. `finally` не гарантируется при аварийном завершении процесса; при таком сбое или ошибке cleanup файл остаётся для адресного восстановления. Не запускать массовую очистку: по этому журналу администратор должен проверить конкретное оборудование/связи и выполнить только точную очистку этого запуска тем же транзакционным порядком. При неизвестном исходе COMMIT очистка ищет метку в БД, даже если ID не вернулся клиенту. Не удалять журнал до подтверждения отсутствия фикстуры.

## Ручной запуск в Visual Studio

1. Проверить Test project/Ref, три выделенных профиля, пароль equipment_api и отдельное Test-only owner-подключение. Ничего не менять в основной базе. User Secrets приложения для этого теста не нужны.
2. Закрыть все экземпляры Visual Studio. Открыть **Developer PowerShell for Visual Studio** отдельно из меню Пуск: новая Visual Studio должна унаследовать переменные текущего процесса, а не использовать старый testhost. Не включать автозапуск тестов после сборки/Live Unit Testing для этой проверки.
3. Задать публичные параметры ниже, заменив placeholders на Test Ref и UUID. Пароли/строки подключения вводятся через скрытые приглашения, а не через аргументы/команды с открытым текстом:

```powershell
$env:EM_PG_TEST_PROJECT_REF = '<20-символьный Project Ref EquipmentManager-Test>'
$env:EM_PG_TEST_ENGINEER_ID = '<UUID test engineer>'
$env:EM_PG_TEST_SPECIALIST_ID = '<UUID test maintenance_specialist>'
$env:EM_PG_TEST_MANAGER_ID = '<UUID test manager>'
$env:EM_PG_TEST_CRUD_CONNECTION = [System.Net.NetworkCredential]::new('', (Read-Host 'Test: полная строка equipment_api' -AsSecureString)).Password
$env:EM_PG_TEST_CLEANUP_CONNECTION = [System.Net.NetworkCredential]::new('', (Read-Host 'Test: полная строка postgres только для очистки' -AsSecureString)).Password
$env:EM_PG_TEST_ALLOW_CLEANUP = 'EquipmentManager-Test only'
$env:EM_PG_TEST_RUN = 'EquipmentManager-Test'
devenv.exe 'C:\Users\Fushi\Desktop\Методы ИИ\Code\EquipmentManager\EquipmentManager.sln'
```

Формат скрыто вводимой строки: `Host=<TEST host>;Port=5432;Database=postgres;Username=<нужный Test login>;Password=<пароль>;SSL Mode=VerifyFull`. Пароли с `;`/кавычками требуют корректного экранирования connection string (обычно значение в двойных кавычках с удвоением внутренних кавычек); не вставлять строку в вывод/исходник/launchSettings. Если нет прямой IPv6-связи, использовать session pooler из Dashboard тестового проекта. Если сертификат не проверяется, исправить доверие/host, не переходить на Require или отключение проверки TLS.

4. Собрать решение. В **Test Explorer** найти ровно `EquipmentFaultMaintenance_PersistsAcrossConnections_AndEnforcesRoles`, категория `PostgresIntegration`, выбрать **Run Selected**. Не запускать приложение и не переключать его DI. Если тест всё ещё Skip, перезапустить Visual Studio из настроенной консоли и обновить обнаружение тестов.
5. Успех означает: данные созданы/прочитаны после переподключения, все запреты сработали и finally подтвердил удаление только своей фикстуры. В Test Output останутся только безопасная метка, путь журнала и сообщение очистки. При ошибке проверять указанный этап; если cleanup не подтверждён, сохранить журнал восстановления и проверить этот запуск до повтора. Наличие пропущенного теста не считать успешной проверкой PostgreSQL.
6. Закрыть Visual Studio/testhost. Удалить `EM_PG_TEST_*` из **текущего процесса** PowerShell и закрыть консоль. Переменные не сохраняются в пользовательское окружение/реестр и не меняют User Secrets:

```powershell
Get-ChildItem Env:EM_PG_TEST_* | Remove-Item
```

## Сценарий и ожидаемые проверки

Один тест создаёт оборудование → проверяет нормализованный дубль → регистрирует заявку → проверяет запреты ролей через хранилища и отдельно сырые RLS-команды под equipment_api → отклоняет пропуск этапа → начинает работы → отклоняет старую версию → завершает → проверяет запрет повторного завершения и удаления связанного оборудования. После уничтожения первого executor новый читает оборудование, завершённую заявку версии 3 и **ровно одну** историю с совпадающими датой, подписью, работами и результатом.

На свежем соединении без контекста проверяется невидимость именно созданных записей во всех трёх таблицах и отказ записи. Дополнительно проверяется запрет прямого INSERT истории вне триггера, DELETE заявки и подмены автора. Все соединения сценария проверяют прямой session_user/current_user=equipment_api без SUPERUSER/BYPASSRLS; SET ROLE нигде нет. Административное подключение отделено и используется только для подготовки очистки/самой очистки.

Доказательство сохранности — реальные коммиты и новые подключения, а не тест в общей ROLLBACK-транзакции. Полный перезапуск самого PostgreSQL этот тест не выполняет. Идемпотентность при потере ответа, одновременные конкурентные завершения, браузерный вход и UI находятся вне этого одного сценария.

Локально выполнена только `dotnet build EquipmentManager.Tests/EquipmentManager.Tests.csproj --no-restore`: 0 ошибок, 0 предупреждений. Тесты и SQL не запускались, настройки Supabase/User Secrets/приложения не менялись, commit/push не выполнялись. Обоснование блокировки очистки: [PostgreSQL 17 — явные блокировки и ACCESS EXCLUSIVE](https://www.postgresql.org/docs/17/explicit-locking.html).
