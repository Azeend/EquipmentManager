## Статус и решение, которое ещё необходимо принять

По сообщению пользователя база развёрнута, четыре таблицы и ограничения проверены. Это принято как исходное условие, а не результат новой проверки облака. **SQL не запускался, подключения не выполнялись, секреты не читались.** Приложение и schema.sql не изменены. Подготовленные политики — предложение для проверки в тестовой среде, не внедрённая авторизация.

Способ аутентификации и подключения приложения не определён. security_policies.sql реализует **только вариант Supabase Auth + пользовательский JWT**, передаваемый в Supabase Data API. Его нельзя применять как универсальную конфигурацию обычного Npgsql-подключения ASP.NET. Выбор варианта должен предшествовать запуску SQL.

## Матрица разрешений

Бизнес-роли хранятся в защищённом public.profiles.roles. Они не являются PostgreSQL login-ролями: все пользовательские JWT используют PostgreSQL-роль authenticated. Отсутствующий профиль, is_active=false, пустой roles или auth.uid()=NULL не дают доступа. При совмещении ролей разрешения объединяются.

| Операция | engineer | maintenance_specialist | manager |
| --- | --- | --- | --- |
| Чтение оборудования, заявок и истории | Да | Да | Да |
| Создание оборудования | Да | Нет | Нет |
| Регистрация неисправности | Да | Да | Нет |
| Новая → В работе | Нет | Да | Нет |
| В работе → Завершена с работами и результатом | Нет | Да | Нет |
| Произвольный INSERT/UPDATE/DELETE истории | Нет | Нет | Нет |
| Изменение profiles.roles / is_active / собственного профиля | Нет | Нет | Нет |
| Чтение собственного активного профиля с бизнес-ролью | Да | Да | Да |
| Чтение чужих профилей | Нет | Нет | Нет |
| UPDATE/DELETE оборудования, DELETE заявки | Не согласовано: запрещено | Запрещено | Запрещено |

Редактирование и удаление оборудования есть в текущем прототипе с памятью, но не разрешены исходной матрицей ТЗ. Их перенос в БД требует отдельного решения, включая FK RESTRICT. Существующий интерфейс пока не подключается к этой БД. Сводка руководителя не создаётся данным SQL: отдельные таблицы/представления/RPC для неё не добавлены.

## Профили без самостоятельного назначения ролей

authenticated получает SELECT профиля только для auth.uid(), активного и с одной из известных ролей. Политика profiles не запрашивает profiles повторно: рекурсивного RLS нет. Остальные политики читают этот защищённый профиль через EXISTS. SECURITY DEFINER-helper для чтения ролей не требуется.

Ни таблица profiles, ни её столбцы не получают клиентских INSERT/UPDATE/DELETE. Даже собственный display_name этим файлом не разрешено редактировать — минимальная безопасная граница. Профиль и роли создаёт отдельно доверенный администратор после создания реального пользователя Auth. manager не равен администратору ролей. Signup, email, пользовательские метаданные и поля формы не используются для выдачи привилегий. Не добавлен публичный RPC назначения ролей.

Чтение чужих профилей намеренно закрыто. Поэтому join к profiles для отображения имени автора чужой заявки не будет возвращать это имя. Заявки содержат UUID авторов; согласование безопасного справочника отображаемых имён или узкой серверной проекции — отдельная задача. Нельзя открыть все profiles только ради имён: таблица содержит также роли и активность.

## ACL, политики и авторы операций

SQL сочетает GRANT и RLS: одного механизма недостаточно. PUBLIC/anon не получают доступа к четырём таблицам, последовательностям и четырём функциям схемы. authenticated получает SELECT, ограниченный INSERT и UPDATE только нужных столбцов. CREATE/TRIGGER/TRUNCATE/REFERENCES и DELETE ему не выдаются. Право UPDATE профиля отсутствует и на уровне SQL grants, и на уровне RLS.

INSERT оборудования принимает только name, inventory_number, location, status. INSERT заявки — только equipment_id, description, created_by; created_by обязан совпасть с auth.uid(). Статус, дата, подпись и версия формируются схемой. UPDATE заявки разрешает status, started_by, completed_by, work_description, result. started_by/ completed_by должны совпасть с фактическим пользователем соответствующего перехода. BEGIN/AFTER guards сохраняют прежние инварианты и временные метки. Любой активный специалист может завершить взятую другим специалистом заявку: запрет этого не задан ТЗ; started_by сохраняется неизменным.

Будущий клиент/API должен выполнять UPDATE с фильтрами id, version и ожидаемым status. Версия увеличивается существующим триггером. Эти политики **не требуют технически наличия version в WHERE**: произвольный Data API PATCH может его пропустить. Для обязательной проверки ожидаемой версии на каждом запросе нужен отдельный командный API/RPC с параметром expectedVersion и запретом прямого UPDATE. Это ограничение исходной схемы не скрывается RLS; RPC здесь не добавлен без выбора архитектуры.

При неразрешённом UPDATE RLS может дать ноль изменённых строк, а не явное исключение. Для INSERT нарушение WITH CHECK обычно даёт ошибку. Приложению нужно различать отсутствие, конфликт и отказ с учётом доступности объекта, не объявлять успех по одному HTTP-коду.

## SECURITY INVOKER и атомарная история

Три существующие триггерные функции остаются SECURITY INVOKER. Они не становятся владельцами таблиц и не обходят RLS. При завершении:

1. UPDATE проходит grants и USING специалиста.
2. BEFORE guard_fault проверяет допустимую пару OLD/NEW, неизменность исходных полей и увеличивает версию.
3. WITH CHECK проверяет новый статус и реального автора перехода.
4. AFTER faults_create_history делает INSERT истории с правами того же authenticated.
5. INSERT требует GRANT INSERT, SELECT связанной заявки, EXECUTE trim_whitespace для CHECK и разрешающей RLS-политики. Без этих прав завершение откатилось бы.
6. guard_maintenance_record сверяет снимок, PK fault_id запрещает дубль. Любая ошибка откатывает UPDATE вместе с INSERT в рамках одной команды/транзакции. ON CONFLICT DO NOTHING не используется.

INSERT истории приходится выдать на уровне ACL из-за INVOKER; политика разрешает его только активному специалисту, для completed_by=auth.uid(), performed_by=auth.uid() и точного снимка завершённой заявки. Дополнительно требуется pg_trigger_depth()=1: при штатном вложенном INSERT выполняется AFTER-триггер заявки; при обычном прямом INSERT после завершения BEFORE-триггера глубина равна 0 и WITH CHECK отклоняет операцию. Это **не криптографическое доказательство источника команды**: глубина не заменяет роли, авторов, сверку снимка и PK. Добавление новых триггеров/RPC/пользовательского DDL требует повторного анализа. Клиенту нельзя давать возможность создавать триггеры или выполнять произвольный SQL с повышением прав. Срабатывание политики на конкретной версии PostgreSQL обязательно подтвердить тестом; здесь оно не проверено запуском.

trim_whitespace(text) — чистая функция без доступа к таблицам, ей возвращён EXECUTE authenticated для CHECK/generated-выражений. Это также может сделать её вызываемой как вычислительный RPC в public; она не раскрывает записи и не повышает права. Если требуется полностью закрыть все RPC, размещение helper-функции нужно менять отдельной миграцией с учётом зависимостей.

EXECUTE трёх триггерных функций клиенту не выдаётся. Триггеры уже созданы владельцем, которому требовались права TRIGGER и EXECUTE при CREATE TRIGGER; выполнение существующего триггера не превращает его в клиентский RPC. Если среда сообщает отказ, проверять grants вложенных запросов, а не автоматически менять SECURITY INVOKER на DEFINER. Все существующие search_path и квалифицированные ссылки сохраняются. Новых функций, особенно SECURITY DEFINER, файл не создаёт.

## Разделение вариантов подключения

### Вариант A: Supabase Auth и Data API с пользовательским JWT

Это единственный вариант, для которого подготовлен исполняемый SQL. Supabase проверяет JWT, выбирает authenticated, auth.uid() берётся из проверенного контекста. Бизнес-роли читаются из profiles при запросе, а не из raw_user_meta_data. Неактивный профиль блокируется политиками независимо от наличия ещё действующего JWT.

Возможны браузер → Data API либо браузер/Blazor → ASP.NET Core API → Data API с **JWT данного пользователя**. Второй путь добавляет серверные команды и DTO, но не должен заменять пользовательский JWT ключом service_role. API проверяет сеанс, роль и входные данные; RLS остаётся дополнительной границей. В InteractiveServer нельзя хранить пользовательский токен в общем singleton-клиенте или смешивать контексты пользователей.

### Вариант B: ASP.NET Core API и прямое подключение PostgreSQL

Предпочтительный основной путь в ТЗ не определяет автоматически механизм идентификации. До реализации требуется выбрать поставщик входа и отображение пользователя на profiles.id (сейчас UUID связан именно с Supabase Auth).

Безопасные варианты: отдельная ограниченная роль API без владения/BYPASSRLS, без клиентского SQL и с серверными проверками; либо ограниченная login-роль, которая в каждой транзакции устанавливает согласованный RLS-контекст и SET LOCAL ROLE. Конкретные роли, политики и claims должны быть отдельной миграцией после выбора схемы. Нельзя считать, что auth.uid() сам появился при обычном PostgreSQL-подключении: обычно он NULL без корректного request-контекста.

Если API устанавливает request.jwt.claims/sub, это доверенная операция сервера **после проверки токена**, внутри транзакции с SET LOCAL и гарантированным сбросом контекста в пуле. Значения из тела запроса не являются подтверждённой личностью. Возможность произвольного SQL под такой login-ролью позволит подделывать контекст, поэтому её нельзя выдавать пользователям. Этот документ не выдаёт login-права и не выбирает настройки пула или JWT за пользователя.

service_role и владелец обходят RLS и не подходят для универсального пользовательского CRUD. Административное управление профилями может иметь отдельно контролируемый канал с журналированием; такой канал не реализован данным SQL и не должен становиться общим маршрутом API.

## Подготовка применения: только после выбора варианта A

1. Проверить актуальные определения четырёх таблиц, CHECK/FK и трёх триггеров по schema.sql. Успешная прежняя проверка ограничений не подтверждает новые политики.
2. Проверить ACL, включая столбцы, наследование PostgreSQL-ролей и отсутствие у authenticated/anon CREATE в доступных схемах, TRIGGER и BYPASSRLS. Файл останавливается при существующих политиках или отдельных column grants, но не заменяет полный аудит наследованных прав и посторонних RPC.
3. Проверить роли и профили отдельных тестовых пользователей. Не назначать реальные роли из UI приложения и не создавать auth.users вручную.
4. Сначала выполнить в отдельной тестовой среде весь security_policies.sql (BEGIN/COMMIT), затем матрицу тестов. Повторный запуск намеренно отклоняется до изменения ACL при обнаружении политик. Существующие неизвестные политики не удаляются и не объединяются через OR молча.
5. Файл открывает ранее закрытые таблицы для согласованных authenticated-операций. Это изменение границы доступа, требующее осознанного решения перед запуском. SQL Editor под владельцем не проверяет обычный RLS: использовать реальные тестовые JWT либо SET LOCAL ROLE authenticated с доверенно заданным тестовым sub только в контролируемом тесте.

Автоматический RLS не мешает явному ENABLE. Отключённая Automatically expose new tables не мешает явным GRANT; Data API должен иметь public среди exposed schemas. Публикация новых политик не даёт доступа anon. Сам файл не меняет настройки Dashboard и default privileges посторонних объектов.

Для контрольного аудита каталогов: pg_policies, has_table_privilege/has_column_privilege, has_sequence_privilege, has_function_privilege, pg_proc.prosecdef/proconfig и pg_trigger.tgenabled/pg_get_triggerdef. Ожидается 8 политик (1 profiles, 2 equipment, 3 faults, 2 history); явных SECURITY DEFINER-функций не добавлено. У authenticated SELECT таблиц и ограниченные column INSERT/UPDATE, INSERT истории и USAGE последовательностей; у anon этих прав нет. Проверять не только табличный UPDATE-флаг: права выданы по столбцам.

## Ограничения и созданные файлы

Созданы только database/security_policies.sql и database/security_description.md. schema.sql, приложение, существующие документы и пакеты не изменены. SQL, сборка и тесты приложения не запускались: C#-тесты не подтверждают PostgreSQL RLS. Облако не проверялось; секреты не использовались. Commit и push не выполнялись.

До применения остаются выбор архитектуры/аутентификации, runtime-проверка всего набора политик с INVOKER-триггерами, решение по обязательной optimistic concurrency для прямого API, безопасное отображение имён авторов и согласование UPDATE/DELETE оборудования. Идемпотентность регистрации после потери ответа и автоматическое создание профиля также не реализованы. Владельцы, service_role/BYPASSRLS и посторонние SECURITY DEFINER/RPC требуют отдельного аудита.
