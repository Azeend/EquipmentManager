В текущем запуске успешное соединение Npgsql с VerifyFull подтверждено независимо; версия сервера и согласованная версия TLS отдельно диагностической программой не измерялись. Помощник использует POST с `{}` для отрицательной проверки прав: даже при ошибочно назначенном engineer тело не проходит валидацию и не создаёт оборудование. Для проверки 403 пользователь не должен одновременно иметь engineer. Отдельный пользователь без разрешённых активных ролей должен получать 403 и на GET; отсутствие engineer само по себе не запрещает чтение manager/maintenance_specialist.

Предусловия помощника: разрешённый Email/Password-вход для тестовых пользователей и подтверждённый email, если требуется настройками проекта. При OAuth/MFA/CAPTCHA использовать штатный Auth-поток, не отключать защиту ради теста. Не запускать с transcript, трассировкой или прокси, записывающим пароли и Authorization. Токены не сохраняются на диск; очистка переменных не гарантирует стирания строк из памяти .NET.

401 означает отсутствие/отказ проверки JWT; 403 — недостаточные полномочия активного серверного профиля; 503 — недоступность источника профилей. Auth HTTP 200 сам по себе не доказывает успешную авторизацию API.

## Источник полномочий

По исходникам ProfileAuthorizationHandler использует UUID sub после проверки JwtBearer, затем вызывает IProfileStore. Решение принимается по public.profiles.roles/is_active. Роли из JWT user_metadata или app_metadata не используются для назначения полномочий. Настоящий PostgresProfileStore в текущей проверке успешно прочитал профиль из Supabase. Сквозной путь «реальный вход → проверка JWT через JWKS → профиль по sub → HTTP 200/403» пока не проверен.
