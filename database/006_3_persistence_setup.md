> Исторический документ этапа подготовки. Описания будущих работ, числа тестов и ограничения отражают состояние того этапа. Актуальная реализация, рабочие настройки и единственный порядок установки для текущего приложения — в [backend_documentation.md](../backend_documentation.md); итог тестирования — в [backend_testing.md](../backend_testing.md). ## Статус

Добавлены асинхронные `PostgresEquipmentStore`, `PostgresFaultStore`, `PostgresMaintenanceStore` и общая транзакционная обёртка `PostgresStoreExecutor` на уже установленном Npgsql. Добавлена отдельная миграция [006_3_faults_maintenance_security.sql](006_3_faults_maintenance_security.sql), строго после 006_1. **Новые классы не зарегистрированы в Program.cs: приложение по-прежнему использует память.** Нет автоматического подключения, запуска SQL, миграции демонстрационных данных или резервного переключения на память при ошибке БД.

Пользователь сообщил, что 006_1 проверена в EquipmentManager-Test, но не установлена в основной базе. Это исходное условие; новая 006_3 не считается выполненной/проверенной ни в одном проекте. Проверенная 006_1, рабочие интерфейс, JWT/cookie-аутентификация, модели и синхронные сервисы не изменены. User Secrets не читались/не изменялись этой подготовкой. Новые пакеты не добавлялись.

## Контракты и соответствие моделям

| Хранилище | Операции | Права активного профиля |
| --- | --- | --- |
| PostgresEquipmentStore | GetAsync с подстрокой, GetByIdAsync, SaveAsync, DeleteAsync | Чтение: три бизнес-роли; запись: engineer |
| PostgresFaultStore | GetAsync, RegisterAsync, ChangeStatusAsync с expectedVersion | Чтение: три роли; регистрация: engineer/maintenance_specialist; обработка: maintenance_specialist |
| PostgresMaintenanceStore | GetAsync с nullable EquipmentId | Чтение: три роли; методов записи нет |

Существующие `Equipment`, `Fault`, `MaintenanceRecord`, `FaultRegistration`, `FaultCompletion`, `EquipmentSaveResult`, `EquipmentDeleteStatus` сохранены. Новый `FaultWriteResult` различает Saved, Invalid, NotFound, Conflict, InvalidTransition. Даты читаются через Npgsql как UTC DateTimeOffset; StartedAt/CompletedAt остаются nullable. ID сохраняют тип int. Версию, подпись оборудования и даты заявки назначают исходные PostgreSQL-триггеры, а не C#.

В `Fault.Author` пока возвращается строка UUID `created_by`, **не имя автора**. Это осознанная граница: существующая 006_1 разрешает роли читать только собственные id/roles/is_active профиля. Прямой JOIN к чужим display_name либо даст отказ, либо потребует расширения прав. Такой JOIN и расширение доступа не добавлены. Перед подключением списка заявок нужно принять отображение UUID или отдельно спроектировать безопасную проекцию имён; нельзя превращать отсутствие имени в отсутствие заявки. Автор, начавший и завершивший работы, записываются по фактическому UUID независимо от отображения.

## Пользователь, подключение и транзакция

Каждый метод принимает `ClaimsPrincipal` из доверенного серверного механизма. Будущий API должен передавать именно `HttpContext.User` **после существующей Bearer-проверки**, а не создавать principal из JSON/UUID/заголовка клиента. Конструктор ClaimsPrincipal сам по себе ничего не проверяет: криптографическая проверка остаётся обязанностью уже работающей аутентификации. Входные DTO не содержат UUID авторов; сырые UUID пользователя хранилища не принимают.

Последовательность `PostgresStoreExecutor.RunAsync` на одном соединении:

1. Проверить единственный непустой sub в аутентифицированных identities.
2. Открыть отдельное соединение CRUD и транзакцию READ COMMITTED.
3. Проверить фактические session_user/current_user = equipment_api, отсутствие SUPERUSER/BYPASSRLS.
4. Параметризованно выполнить `set_config('equipment.user_id', $1, true)` с UUID из principal.
5. Через существующий SECURITY INVOKER `equipment_api_security.has_any_role` проверить активный профиль и требуемые для операции роли.
6. Выполнить параметризованные запросы в той же транзакции; RLS проверяет каждую команду независимо от прикладной проверки.
7. Вернуть успех только после COMMIT. Незавершённая транзакция откатывается при DisposeAsync; ошибки не подавляются. CancellationToken проходит во все операции.

Контекст локален транзакции и не остаётся в следующей операции пула. `No Reset On Close=true` и multiplexing запрещены; автоматическое enlist в ambient TransactionScope отключено. Команды имеют timeout 15 секунд. Нет автоматических повторов записи.

Отдельный пул executor создаётся из явно переданной строки; он не использует зарегистрированный для профилей NpgsqlDataSource. Имя login должно быть `equipment_api` либо `equipment_api.<projectref>` для Supavisor, база postgres, SSL Mode=VerifyFull. postgres, service_role, equipment_app/любой профильный читатель и любые иные login отклоняются до подключения. На сервере дополнительно проверяется реальная роль, так что имя в строке не заменяет серверную проверку.

**Сейчас строку подключения добавлять не нужно.** После отдельного разрешения на включение её следует хранить отдельно (например ConnectionStrings:EquipmentCrud) в User Secrets/окружении. Не копировать существующее подключение Profiles для CRUD и не вводить пароль в SQL/репозиторий/лог. При регистрации в DI один исполнитель должен совместно обслуживать все три хранилища, а пул должен освобождаться при остановке хоста. В этой подготовке никаких регистраций/настроек не добавлено.

Custom GUC не проверяет JWT и не является защитой от владельца credentials equipment_api или SQL injection в доверенном backend. Credentials остаются только на сервере, запросы параметризованы, универсальный SQL endpoint не предоставляется. Роль, владение, членство и политики после миграции не должны произвольно расширяться.

## Сохранённые правила

- Имя, номер, место и состояние проверяются существующим EquipmentValidator; крайние пробелы удаляются из копии ввода, форма не изменяется.
- Нормализованный номер окончательно защищён UNIQUE `equipment_inventory_number_unique`. Только его 23505 преобразуется в Conflict. C# не делает предварительный SELECT-поиск дубля, который не защитил бы от гонки.
- Семантика уникальности — исходный PostgreSQL lower(trim_whitespace(...)); она не выдаётся за точное Unicode-совпадение OrdinalIgnoreCase. Перечень краевых Unicode-примеров нужно проверить на целевой collation. Подстрочный поиск параметризован через strpos; `%`/`_` не являются wildcard, расширения и индексы не добавляются.
- Удаление проверяется окончательно FK RESTRICT. Только ожидаемые FK оборудования дают Linked; посторонняя ошибка не маскируется. Заявки и история не удаляются.
- Регистрация выполняется INSERT ... SELECT из видимого существующего equipment с автором из транзакции. Ноль строк/исчезновение оборудования из-за конкурентного удаления дают NotFound; произвольные FK-сбои не подменяются этой ошибкой.
- Только Новая → В работе → Завершена. Оба поля завершения обязательны после Trim; пропуск, обратный/неизвестный переход и устаревшая версия отклоняются.
- После чтения версия и исходный статус повторно проверяются в WHERE самого UPDATE. При двух конкурентных командах второй UPDATE после ожидания перепроверяет условие и возвращает Conflict, не перезаписывая первую запись. UPDATE version/date из C# отсутствует.
- Завершение делает только UPDATE faults. AFTER-триггер `faults_create_history` сам вставляет единственную историю; PK FaultId и составной FK сохраняются. Ошибка истории прерывает UPDATE и всю транзакцию. Повторное завершение не создаёт второй записи.
- История читается по оборудованию или всему парку, сортируется по performed_at DESC, fault_id DESC. Работы, результат и подпись — исходный неизменяемый снимок заявки; техническое состояние оборудования автоматически не меняется.

Сетевые/SQL-ошибки не заменяются пустой коллекцией. `StoreException` содержит безопасный Failure/SQLSTATE/ConstraintName без строки подключения, пользовательских значений и PostgreSQL Detail. Не отдавать эти машинные сведения клиенту автоматически; будущий API отображает бизнес-ошибки, 403/503 и traceId. Отмена до COMMIT распространяется вызывающему коду. При сетевом отказе/отмене во время COMMIT возвращается OutcomeUnknown: результат нужно сверить, нельзя обещать откат и автоматически повторять INSERT. Полная идемпотентность регистрации новой заявки пока не реализована.

## Дополнительная миграция 006_3

Миграция транзакционная, однократная. Проверяет наличие ограниченной equipment_api и пяти политик 006_1, RLS, исходных включённых INVOKER-триггеров и связи истории. Конфликтующие PUBLIC/equipment_api-политики заявок/истории приводят к отказу. Проверки служат preflight зависимостей, а не доказательством идентичности всех определений и не заменяют ранее согласованный аудит 006_1.

Выдаются только:

- SELECT faults и maintenance_records (включая поля, необходимые существующим guards).
- INSERT faults: equipment_id, description, created_by.
- UPDATE faults: status, started_by, completed_by, work_description, result.
- INSERT семи полей maintenance_records, явно используемых существующим INVOKER AFTER-триггером.
- USAGE faults_id_seq, без SELECT/UPDATE последовательности.

Пять новых политик TO equipment_api: чтение заявок, создание заявки, смена статуса, чтение истории, вставка истории при завершении. Авторы проверяются через current_profile_id; роль — через has_any_role. Вставка истории требует глубины триггера 1, фактического специалиста, завершённой исходной заявки и совпадения полного снимка. `pg_trigger_depth` — дополнительное условие, не доказательство личности. Существующий guard истории независимо проверяет снимок; PK препятствует дублированию.

Версия, дата, подпись и исходные сведения заявки не получают прямых column UPDATE grants. История не получает UPDATE/DELETE; новые роли/SECURITY DEFINER-функции/таблицы/изменения Auth не создаются. EXECUTE триггерных функций не выдаётся: существующие триггеры не требуют его у пользователя DML. Чистая trim_whitespace уже разрешена в 006_1 для CHECK. Доступ PUBLIC/anon/authenticated/equipment_app и инфраструктурная rls_auto_enable не меняются.

После выдачи проверяются фактические табличные/столбцовые права и последовательность, включая доступ через PUBLIC; неожиданные grants приводят к откату без глобального REVOKE. Действующий backend и проверенная 006_1 не изменяются. **006_1 нельзя повторно запускать после 006_3:** она однократная и её исходная проверка намеренно запрещала новые права faults/history, появляющиеся только на этом этапе.

## Проверки перед включением — только будущие ручные действия

Сначала использовать EquipmentManager-Test и **реальную ограниченную login equipment_api**, не SQL Editor владельца в качестве доказательства RLS. Сейчас агент ничего из следующего не выполнял:

1. Сверить target host/project и схему с исходной schema.sql, сохранить определения/ACL/политики; удостовериться в успешной 006_1 и отсутствии уже применённой 006_3. Сверить реальные имена FK и UNIQUE с классификацией в C#; не переименовывать ограничения молча.
2. После отдельного разрешения применить весь файл 006_3 на тестовом проекте. Проверить SELECT/column INSERT/UPDATE, отсутствие DELETE/TRUNCATE/MAINTAIN, отсутствие лишних прав последовательности, роли и владения. Preflight не отключать ради прохождения.
3. Для уже существующих активных профилей engineer / maintenance_specialist / manager проверить матрицу: чтение трём ролям; регистрация первым двум; обработка только специалисту. Без контекста/с неверным UUID/неактивным профилем доступа нет. Чужие author/performer UUID должны отклоняться RLS. Не создавать/менять профили в основной базе ради теста.
4. Создать тестовое оборудование, заявку, взять в работу и завершить. Убедиться: серверные UTC-даты и подпись, ожидаемое увеличение версии, ровно одна связанная история с тем же EquipmentId, actor и содержимым. Проверить запрет прямого INSERT истории, UPDATE/DELETE истории, пропуска/возврата статуса и пустых работ/результата.
5. Вызвать отказ вставки истории **только на изолированном стенде**, не меняя production guards: завершение должно полностью откатиться, версия/статус/дата остаться прежними, истории нет. Модульный fake не подтверждает это свойство PostgreSQL.
6. Два отдельных соединения с одной ожидаемой версией: одно завершение успешно, второе Conflict; одна история. Два конкурентных нормализованных номера: один успех, один Conflict. Связанное оборудование не удаляется даже при конкурентной регистрации заявки.
7. На пуле MaxPoolSize=1 проверить смену пользователей: успешная транзакция/COMMIT, отказ/ROLLBACK, cancellation, затем новая операция без старого контекста. Каждая операция должна устанавливать свой UUID. Проверить потерю ответа на COMMIT и процедуру сверки без автоматического повтора.
8. Проверить кириллицу/регистр/краевые Unicode-пробелы номера на выбранной collation, точное чтение nullable UTC дат и пустой источник. Сбой источника должен отображаться ошибкой. Подтвердить приемлемость UUID в Author до внедрения безопасной проекции имён.

## Что ещё нужно для завершения 6.3

После успешных PostgreSQL-проверок и отдельного решения о развёртывании: применить проверенную 006_1 в основной базе, затем 006_3; отдельно настроить защищённое CRUD-подключение equipment_api. В этом шаге эти действия запрещены и не выполнялись.

Затем отдельной правкой подключить новый executor и **все три** хранилища в DI, перевести backend-операции на async и передавать проверенный principal. Существующий API оборудования сейчас вызывает синхронный memory-service; HTTP API заявок/истории ещё требуется добавить. Страницы пока напрямую вызывают старые сервисы; их интеграция с API — следующий этап без изменения текущей авторизации. Нельзя включать только оборудование в БД и оставлять связанные заявки в памяти. Демо-объекты/фиктивные авторы автоматически не переносятся; стратегию начального наполнения согласовать отдельно.

Перед рабочим включением пройти весь пользовательский путь и повторить чтение после перезапуска процесса: оборудование, заявки, история и связи должны сохраняться. Пока это не сделано, раздел 6.3 имеет статус **реализация подготовлена, постоянное хранение не включено**.

## Автоматические проверки и ограничения

Новые модульные тесты используют подмену границы SQL: проверяют бизнес-отказы, параметры команд, проекции моделей/nullable UTC дат, точную классификацию UNIQUE/FK, защиту от устаревшей версии/гонки, отсутствие дублирующего INSERT истории и распространение ошибки триггера. Отдельно проверяются UUID principal и ограничения строки подключения без открытия соединения. Подмена не эмулирует PostgreSQL и не доказывает его RLS/транзакционные свойства.

Команды локальной проверки: `dotnet build EquipmentManager.csproj --no-restore` и `dotnet test EquipmentManager.Tests/EquipmentManager.Tests.csproj --no-restore`. SQL проверен логически, **не запускался на PostgreSQL/Supabase и не проверен серверным парсером**. Контекст пула, конкурентность, реальный откат и права триггеров остаются обязательными интеграционными проверками. Никакие облачные тесты не объявляются пройденными.

Фактический результат: сборка — 0 ошибок и 0 предупреждений; все 113 тестов прошли, в том числе 39 новых модульных и 74 существующих, пропусков нет. SHA-256 006_1, Program.cs и существующих сервисов/API совпали со снимком до этого этапа. Восемь новых файлов проверены на завершающие пробелы; SQL также проверен структурно (парные dollar-delimiters и баланс скобок), что не является серверным синтаксическим анализом. Commit/push не выполнялись.
