## Область применения и безопасность

Регистратор MapDevelopmentEquipmentApi вызывается из Program.cs и проверяет IsDevelopment(). Только в Development создаются маршруты /api/equipment. В Production, Staging и других средах эти endpoints **не регистрируются**. Авторизация для них пока отсутствует; это учебный локальный интерфейс, не публичный API.

Существующие Blazor-страницы не менялись. Ограничение средой относится к новым REST-маршрутам, а не является реализацией защиты всего приложения. Development следует запускать только локально и не публиковать в интернете; среда должна задаваться конфигурацией хостинга, а не данными запроса. CORS и права Supabase этим изменением не настраивались.

API не использует service_role и не обходит RLS. Варианты будущей аутентификации описаны в security_description.md и ещё требуют выбора. Подготовленные security_policies.sql не применяются автоматически. PUT и DELETE добавлены по текущему заданию для памяти, а не как согласованные права будущих production-ролей.

## Хранение и общая бизнес-логика

API и Blazor используют один singleton EquipmentDataService. Изменения видны при следующем чтении данных тем же процессом; автоматическая рассылка обновлений открытым страницам не добавлена. После перезапуска изменения теряются, восстанавливаются пять начальных записей.

Существующий Save оставлен для страниц и возвращает прежний список ошибок. Новый SaveWithResult использует ту же проверку и блокировку, но возвращает типизированный исход и копию сохранённой записи с ID. Это позволяет выдавать точный 201/Location без поиска созданной записи после снятия блокировки и без разбора русских строк ошибок. Запись и проверка номера выполняются атомарно под общей блокировкой, включая конкурирующие запросы UI/API.

ID назначается сервером для POST и берётся из маршрута для PUT. Входной DTO EquipmentRequest содержит только четыре поля. Null и отсутствующие строки приводятся к пустым значениям для общего валидатора. Входной объект не даёт клиенту назначать ID; неизвестные JSON-поля стандартно игнорируются, не являются частью контракта.

## Контракты

Base URL локального HTTP-профиля: http://localhost:5156.

| Метод и путь | Вход | Успех | Отказы |
| --- | --- | --- | --- |
| GET /api/equipment | Необязательный query | 200, JSON-массив, в том числе [] | Ошибки инфраструктуры не подменяются пустым массивом |
| GET /api/equipment/{id} | Целочисленный ID | 200, объект | 404 |
| POST /api/equipment | JSON четырёх полей | 201, объект и Location: /api/equipment/{id} | 400 валидация, 409 занятый номер |
| PUT /api/equipment/{id} | ID и полный JSON четырёх полей | 200, обновлённый объект | 404 отсутствующий/неположительный ID; 400 валидация; 409 занятый номер |
| DELETE /api/equipment/{id} | Целочисленный ID | 204, без тела | 404, в том числе повторное удаление |

PUT заменяет все четыре поля, не является PATCH и не создаёт отсутствующую запись. При отсутствующем ID приоритет имеет 404; для существующей записи некорректные поля дают 400, а корректные поля с занятым номером — 409. Нецелочисленный сегмент не совпадает с маршрутом и даёт 404. Некорректное JSON-тело/несовместимые JSON-типы обрабатываются стандартным binder ASP.NET Core с 400; неподдерживаемый Content-Type может дать 415. Эти транспортные ответы не используют прикладной формат ошибок ниже.

GET query ищет часть Name ИЛИ InventoryNumber с CurrentCultureIgnoreCase, удаляет крайние пробелы запроса. Пустой/пробельный query возвращает весь реестр. Порядок — текущий порядок списка сервиса, без пагинации. Фильтры status, departmentId, версии оборудования и totalCount из целевого API ТЗ пока не реализованы. Реальный маршрут имеет префикс /api; это учебный поднабор ТЗ, не весь будущий контракт.

### Тело POST / PUT

Content-Type: application/json.

```json
{
  "name": "Насос API",
  "inventoryNumber": "API-2001",
  "location": "Цех №2",
  "status": "Исправно"
}
```

Все четыре поля обязательны. Name, InventoryNumber и Location не могут быть пустыми/пробельными; по краям сохраняемых строк удаляются пробелы. Status должен точно совпадать с одним из значений:

- Исправно;
- Требует обслуживания;
- Неисправно.

Уникальность номера: Trim + StringComparison.OrdinalIgnoreCase, при PUT собственная запись исключается. Номер ` inv-1001 ` конфликтует с исходным `INV-1001`. Проверка выполняется сервисом для создания и обновления, не только HTTP-обработчиком. Некорректное сохранение не меняет данные.

### Представление оборудования

```json
{
  "id": 6,
  "name": "Насос API",
  "inventoryNumber": "API-2001",
  "location": "Цех №2",
  "status": "Исправно"
}
```

ID 6 — пример для свежего процесса без ранее созданных записей, не обещание конкретного ID. GET списка возвращает массив таких объектов; без совпадений — `[]` с кодом 200.

### Прикладные ошибки

Валидация, конфликт и отсутствие записи возвращают application/problem+json с code, traceId и errors. Общий валидатор пока выдаёт список ошибок, поэтому errors сгруппированы под ключом equipment, без искусственного разбора текста для привязки к полям.

Пример конфликта (traceId иллюстративный):

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.10",
  "title": "Операция с оборудованием не выполнена.",
  "status": 409,
  "code": "inventory_number_conflict",
  "traceId": "example-request-id",
  "errors": {
    "equipment": [
      "Оборудование с таким инвентарным номером уже существует."
    ]
  }
}
```

Стандартное поле type заполняется ASP.NET Core и не предназначено для клиентского сопоставления бизнес-ошибок. Устойчивые прикладные коды: validation_failed (400), equipment_not_found (404), inventory_number_conflict (409). Прикладные ответы не содержат исключений или стека. Стандартная диагностическая страница Development и ошибки связывания JSON — отдельный механизм; централизованный production-контракт ошибок ещё не реализован.

## Локальный запуск и запросы

Из корня проекта:

```powershell
dotnet build EquipmentManager.sln
dotnet test EquipmentManager.sln --no-restore
dotnet run --no-build --project EquipmentManager.csproj --launch-profile http
```

Профиль http задаёт ASPNETCORE_ENVIRONMENT=Development и localhost:5156. Для ручного запуска без профиля среду и адрес нужно указывать явно. Не используйте Development для публичного размещения.

Примеры PowerShell во втором терминале (это инструкции, не результат отдельного ручного прогона):

```powershell
$apiBase = 'http://localhost:5156/api/equipment'
Invoke-RestMethod -Uri $apiBase
Invoke-RestMethod -Uri ($apiBase + '?query=INV-1001')
Invoke-RestMethod -Uri ($apiBase + '/1')

$apiBody = @{
    name = 'Насос API'
    inventoryNumber = 'API-2001'
    location = 'Цех №2'
    status = 'Исправно'
} | ConvertTo-Json

$createdEquipment = Invoke-RestMethod -Method Post -Uri $apiBase `
    -ContentType 'application/json; charset=utf-8' -Body ([System.Text.Encoding]::UTF8.GetBytes($apiBody))

Invoke-RestMethod -Method Put -Uri ($apiBase + '/' + $createdEquipment.id) `
    -ContentType 'application/json; charset=utf-8' -Body ([System.Text.Encoding]::UTF8.GetBytes($apiBody))

Invoke-RestMethod -Method Delete -Uri ($apiBase + '/' + $createdEquipment.id)
```

DELETE из примера удаляет только созданную примером запись. Не используйте его для исходного оборудования без намерения удалить его. Остановка процесса — Ctrl+C; перед следующей сборкой остановите приложение, чтобы exe не был заблокирован.

## Ограничения перед следующим этапом

- DELETE сохраняет нынешнюю семантику памяти: связанные заявки/история не удаляются и не блокируют удаление оборудования. Это отличается от ON DELETE RESTRICT в schema.sql и требует изменения сервиса при подключении БД, а не фиктивного объявления нынешнего поведения совместимым с FK.
- PUT не содержит версии/ETag: параллельные корректные обновления сериализованы блокировкой, но действует последнее сохранение. Оптимистическая конкуренция и идемпотентность команд пока не реализованы.
- Для Production нужно отдельно определить аутентификацию, роли, политику PUT/DELETE и безопасное подключение. Простое снятие Development-проверки недопустимо.
- Нет пагинации, фильтра подразделения, настоящей БД, новых SQL-объектов или изменений схемы. Существующие страницы не переведены на HTTP.
