# ДЗ6, шаг 4: Яндекс Метрика

Счётчик: **113657931**. Номер публичный, не является секретом и находится в
`Analytics:YandexMetrika:CounterId`, а не в исходном JS. По умолчанию аналитика выключена.

## Включение на Render

После проверки и публикации кода добавить/проверить Environment:

```text
ASPNETCORE_ENVIRONMENT=Production
Analytics__YandexMetrika__Enabled=true
Analytics__YandexMetrika__CounterId=113657931
Analytics__YandexMetrika__PublicOrigin=https://equipment-manager-demo.onrender.com
```

PublicOrigin — только HTTPS origin, без пути, query или fragment. Не вычисляется из Host запроса.
Для смены счётчика достаточно изменить CounterId в окружении. Для отключения — Enabled=false.
Development, localhost, другой origin и некорректная конфигурация не отправляют просмотры.
Настройки Supabase, PostgreSQL, Яндекс OAuth и cookies менять не нужно.

Перед включением проверить настройки **самого счётчика** в интерфейсе Метрики:
Вебвизор, аналитика/запись форм, автоматические цели и автосбор данных, ecommerce,
Advanced Matching и Яндекс Тег Менеджер должны быть выключены. Не добавлять в счётчик
другие теги, передающие данные посетителя. Эти облачные настройки из проекта не изменяются;
функции автосбора, заданные в интерфейсе сервиса, требуют отдельной проверки владельцем.

## Просмотры и Blazor InteractiveServer

`MetrikaTracker` расположен в Router внутри AuthorizeView. Он вызывается после интерактивной
отрисовки маршрута и получает Navigation.Uri только на сервере. SSR не выполняет JS и не
вставляет сторонний script или noscript-пиксель. Query, fragment и произвольные сегменты
отбрасываются до JS interop. Повторная проверка текущего browser URL выполняется в JS.

Модуль `wwwroot/js/metrika.js` один раз асинхронно загружает официальный
`https://mc.yandex.ru/metrika/tag.js` с referrerPolicy=no-referrer. До успешной загрузки
не ставятся в очередь init/hit. Переход во время загрузки отменяет устаревший просмотр.

При init задано `defer:true`: автоматический просмотр отключён. После этого используется
ручной `ym(counterId, "hit", safeUrl, {title: fixedTitle, referer: safeReferrer})`.
Повторные рендеры и гидратация того же маршрута не создают hit; переход A → B → A создаёт
три просмотра. Для текущей структуры приложения отдельный enhancedload-обработчик не нужен:
защищённые страницы используют интерактивный Router, а вход/выход выполняют обычную навигацию.

Разрешены только фиксированные маршруты:

| Путь | Фиксированное название |
|---|---|
| `/` | Главная |
| `/equipment` | Оборудование |
| `/faults` | Неисправности |
| `/maintenance-history` | История обслуживания |
| `/counter` | Счётчик |
| `/weather` | Погода |

Login, logout, `/account/session`, весь OAuth, API, Error и неизвестные маршруты исключены.
Любая страница с query или fragment **полностью пропускается**, даже если pathname разрешён.
Это сознательная потеря части статистики ради защиты чувствительных URL; адрес браузера
и бизнес-функции не изменяются. Новые маршруты автоматически в аналитику не попадают.

При исключённом маршруте или удалении компонента счётчик останавливается через destruct.
После возвращения на разрешённый путь может быть переинициализирован с defer:true.
При недоступности скрипта/блокировщике/ошибке JS отображение страницы и авторизация продолжаются;
повтор загрузки после ошибки возможен при полной перезагрузке документа.

## Передаваемые данные и ограничения

Передаются только канонический HTTPS origin + фиксированный путь и фиксированное название.
Referer задаётся явно: предыдущий безопасный путь либо корень PublicOrigin. Исходный
document.referrer не используется. Init также получает безопасные url/referrer, поскольку
defer отключает автоматический просмотр, но не гарантирует отсутствие служебного запроса.

Явно выключены webvisor, clickmap, trackLinks, trackHash, accurateTrackBounce, ecommerce,
childIframe и sendTitle; задан disableYtm=true. DOM, содержимое форм и document.title
код интеграции не читает. Нет reachGoal, setUserID, userParams, params, firstPartyParams,
email, UUID, JWT, паролей или OAuth-токенов. События авторизации не отправляются.
Cookies авторизации, UiSessionStore, Bearer API и SignalR не изменены.

Метрика остаётся сторонним аналитическим сервисом: сетевые запросы раскрывают ему IP и
обычные технические сведения браузера; сервис может использовать собственные аналитические
идентификаторы/cookies. Это не передача идентификатора пользователя EquipmentManager.
Приложение не реализует отдельный механизм согласия на аналитику: при необходимости его
нужно добавить до включения счётчика для реальных пользователей. Уведомление о применении
аналитики и параметры сервиса определяет владелец опубликованного приложения.

## Проверки

```text
dotnet build EquipmentManager.sln --configuration Release --no-restore
dotnet test EquipmentManager.sln --configuration Release --no-build --no-restore --filter "Category!=PostgresIntegration"
dotnet format EquipmentManager.sln --verify-no-changes --no-restore
node --test EquipmentManager.Tests/metrika.test.mjs
```

xUnit проверяет разрешённые/запрещённые пути и origin, настройки и регрессию password-сеанса.
Отдельные JS-тесты используют настоящий модуль с подменённым DOM и ym: проверяют init/hit,
SPA-навигацию, отсутствие дублей и чувствительных данных, асинхронные гонки и отказ скрипта.
Node использует только встроенные модули, npm-пакеты не требуются. JS-тесты запускаются
отдельной командой; текущий GitHub workflow на этом шаге не изменён.
Автоматические тесты не загружают настоящий tag.js и не отправляют данные счётчику.

После ручного включения на Render проверить в браузере Network и отчёте Метрики:

1. Открыть login: запросов счётчика быть не должно. Войти по паролю или Яндекс ID.
2. Перейти `/equipment` → `/faults` → Back: по одному hit на каждый просмотр;
   технический init с defer не считать отдельным просмотром.
3. Проверить, что page-url/page-ref не содержат query/hash и заголовков с данными пользователя.
4. Открыть `/account/session`, выйти и повторить OAuth: отдельные просмотры этих действий отсутствуют.
5. Заблокировать mc.yandex.ru: приложение, вход и страницы продолжают работать.

Данная работа не проверяет облачный счётчик реальными запросами и не меняет его настройки.
