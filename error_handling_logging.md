# Лабораторная №5, шаг 7: обработка ошибок и логирование

## Проверенное поведение

| Сценарий | API и интерфейс |
| --- | --- |
| Нет JWT или JWT истёк | 401; серверный клиент завершает локальный сеанс и требует повторного входа |
| Нет подходящей роли активного профиля | 403; понятное сообщение о недостаточных правах, без удаления действующего сеанса |
| Недоступен источник профилей | 503, отказ в выполнении операции; не подменяется 403 |
| Ошибка заполнения | 400 и сообщения валидации; форма сохраняет введённые поля |
| Дубликат инвентарного номера | 409; общая нормализация и UNIQUE PostgreSQL сохранены |
| Устаревшая версия заявки или связанные записи | 409; повторная запись автоматически не выполняется |
| Сбой подключения/таймаут Npgsql | 503 и сообщение о недоступности хранилища |
| Потеря подтверждения COMMIT | 503, просьба сверить данные перед повтором |
| Другая ошибка PostgreSQL | 500, безопасное общее сообщение |
| Неожиданное исключение внутри команды API | 500, безопасный ProblemDetails вместо необработанного исключения |

Endpoint filter обрабатывает ошибки выполнения команд API. Отмена HTTP-запроса клиентом не превращается в искусственную ошибку сервера. Ошибки инфраструктуры вне фильтра обслуживаются существующим конвейером ASP.NET Core. Обработчики JWT, авторизация и бизнес-правила не менялись.

## Точечные изменения

- Фильтр API журналирует код отказа, HTTP-статус, SQLSTATE и TraceId. Неожиданное исключение журналируется по типу и TraceId, без объекта исключения, его Message или StackTrace с потенциальными данными.
- Executor указывает этап: open_connection, begin_transaction, verify_login, set_user_context, check_permissions, execute_operation, commit. Не записывает SQL, параметры, UUID, строки подключения, пароли и токены.
- Серверный HTTP-клиент корректно обрабатывает ошибочный JSON, корнем которого является массив/скаляр, вместо вторичного InvalidOperationException.
- Добавлены локальные тесты 500/503/403, неизвестного результата записи, связи ответа с журналом по TraceId и отсутствия исходного текста исключения в ответе и журнале. Существующие тесты проверяют 401/403, 400, дубликат номера и конкурентные изменения.

## Что проверить вручную для отчёта

1. После остановки текущего сеанса отладки пересобрать проект и запустить HTTPS-профиль. Новые обработчики не появляются в уже запущенном старом процессе автоматически.
2. В Visual Studio открыть «Вывод → ASP.NET Core Web Server / Отладка». Для 401 выполнить запрос к `/api/equipment` без заголовка Authorization: API возвращает 401 даже при наличии интерфейсной cookie. Для 403 использовать существующего руководителя и серверный запрос изменения оборудования в локальном тесте; интерфейс намеренно скрывает запрещённые команды. Не помещать JWT в скриншоты и историю команд.
3. В форме оборудования отправить пустые обязательные поля. В зависимости от места проверки клиентская валидация может остановить запрос; REST-проверка 400 подтверждается автоматическими тестами. Затем повторить существующий инвентарный номер с другим регистром и крайними пробелами: ожидается сообщение о дубликате, без новой записи.
4. Для снимков 500/503 использовать локальные `ErrorHandlingTests` с подменой executor, не создавать неисправность в основной базе. Реальный сетевой отказ можно проверить локально кратковременным отключением сети при чтении и восстановлением связи, без изменения подключения. Ошибка может возникнуть на проверке профиля раньше CRUD; в обоих случаях операция должна быть отклонена с понятным сообщением.
5. В Supabase Dashboard основной EquipmentManager открыть Logs/Explorer и выбрать источник PostgreSQL (`postgres_logs`), интервал вокруг известной ошибки и уровень ERROR/FATAL. Сопоставить время и SQLSTATE с локальным журналом; при наличии метаданных ограничить поиск ролью equipment_api. ASP.NET-журналы и локальный TraceId автоматически в Supabase не отправляются. Для прямого Npgsql-подключения нужен источник Postgres, а не только API/PostgREST. См. [официальное описание Postgres Logs](https://supabase.com/docs/guides/troubleshooting/how-to-interpret-and-explore-the-postgres-logs-OuCIOj).

Postgres Logs могут содержать SQL и подробности данных: для отчёта достаточно времени, уровня, SQLSTATE и обезличенного описания. Не копировать полный event_message без просмотра. Клиентский отказ валидации, ошибка до достижения PostgreSQL и обработанный отказ роли не обязаны создавать ERROR в Postgres Logs. Настройки серверного логирования менять не требуется.

Проверки облачных журналов и реальные аварии разработчиком не выполнялись. Отложенный PostgresIntegration-тест сохранён и не запускался. SQL, роли, Supabase и User Secrets не изменялись.
