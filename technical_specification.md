# Техническое задание EquipmentManager

Лабораторная работа №3. Дата: 16.10.2026. Статус: проект требований к развитию существующего прототипа.

## 1. Основания, описание проекта и границы

Основания: [описание проекта](project_description.md), [описание интерфейсов](ui_concepts/ui_description.md), [семь пользовательских историй](user_stories.md), [сценарии ошибок](error_scenarios.md), [правила разработки](AGENTS.md). Фактическое состояние дополнительно проверено по EquipmentManager.csproj, Program.cs, Models/Equipment.cs, Services/EquipmentDataService.cs, Validators/EquipmentValidator.cs, Components/Pages/EquipmentList.razor и Components/Layout/NavMenu.razor. Проверка исходников статическая; запуск приложения и проверка подключения к БД не выполнялись.

EquipmentManager — браузерное приложение для централизованного учёта промышленного оборудования внутри одного предприятия или учебной организации. Оно связывает реестр, неисправности и выполненное обслуживание, сохраняя сведения при смене ответственных сотрудников. Цели — ускорить поиск, сделать состояние парка прозрачным и сохранить историю работ. Сокращение времени поиска является ожидаемым эффектом, а не уже измеренным результатом.

Объём настоящего ТЗ: US-01–US-06 — обязательный сквозной процесс, US-07 — следующий приоритет Should have. Четыре продуктовые функции раскладываются на семь историй: учёт → US-01 и US-03; поиск → US-02; неисправности → US-04 и US-05; история → US-06; обзорная сводка → US-07.

Редактирование и отдельный фильтр места установки входят в продуктовую перспективу, но не в семь исходных историй. Для них ниже выделены самостоятельные планируемые требования EXT, не подменяющие исходные AC. Удаление, повторное открытие завершённых заявок, экспорт, отчётность, телеметрия, учёт загрузки за смену и работа нескольких предприятий не входят в согласованный объём семи историй.

Идентификаторы: FR — функциональное требование, UI — интерфейс, NFR — нефункциональное требование, DATA — хранение, API — будущий контракт, EXT — развитие, GWT — дополнительный приёмочный сценарий. AC сохранены из источника без перенумерации. Все новые проектные решения и численные цели ниже являются предложениями этого ТЗ; они не выдаются за ранее согласованные требования или реализованные функции.

## 2. Аудитория и роли

Ответственные за учёт представлены ролью инженера; специалисты по обслуживанию обрабатывают заявки; руководитель определяет приоритеты по данным парка. Каждый пользователь целевой системы должен проходить аутентификацию. Механизм назначения ролей необходимо определить до внедрения; публичная самостоятельная выдача привилегий запрещена.

| Операция | Инженер | Специалист по обслуживанию | Руководитель |
| --- | --- | --- | --- |
| Реестр, поиск, чтение заявок и истории | Да | Да | Да |
| Добавление оборудования | Да | Нет | Нет |
| Регистрация неисправности | Да | Да | Нет |
| Изменение статуса заявки | Нет | Да | Нет |
| Сводка US-07 | Не предоставлено историями | Не предоставлено историями | Да |
| Редактирование оборудования | Требует отдельного согласования | Требует отдельного согласования | Не предоставлено |

Отсутствие разрешения означает отказ по умолчанию. Матрица применяется на сервере к каждому чтению и изменению, включая прямые запросы; скрытие кнопок недостаточно. Для совмещения ролей предлагается объединение явно выданных разрешений. Администратор как отдельная бизнес-роль исходными историями не задан.

## 3. Стек и архитектура

| Технология | Назначение | Состояние |
| --- | --- | --- |
| C#, .NET 9 | Модели, прикладные правила, целевая платформа net9.0 | Используются |
| ASP.NET Core | Хостинг, серверные команды, защита, будущий REST API | Хостинг используется; API и права планируются |
| Blazor, Interactive Server | Компоненты и интерактивность через серверное соединение | Режим зарегистрирован в Program.cs |
| PostgreSQL | Транзакционное постоянное хранилище | Не подключено |
| Supabase | Вариант размещения PostgreSQL; возможный поставщик идентификации | Предлагается, не подключён |

Предлагается модульный монолит в существующем проекте: Components — отображение и формы; Services — прикладные операции и проверки прав; Models — сущности; Validators — правила ввода. Доступ к PostgreSQL добавляется за интерфейсом хранилища внутри текущей структуры. Выделение отдельных проектов и перестройка каталогов не требуются. Компоненты вызывают прикладные сервисы; будущие HTTP-обработчики используют те же сервисы, чтобы правила не дублировались.

Supabase не является второй параллельной БД: при выборе сервиса используется размещённый в нём PostgreSQL. Предлагаемый основной путь — Blazor → серверный прикладной сервис → PostgreSQL. Браузер не получает привилегированный ключ Supabase или строку подключения. Если позднее будет выбран прямой доступ через Supabase Data API, до его включения необходимы отдельная модель RLS и проверки прав; это не входит в текущий контракт REST API приложения.

Аутентификация может использовать Supabase Auth с серверной проверкой идентичности и прав; окончательный поставщик и способ связи сеанса с пользователем остаются решением реализации. Для транзакций, миграций и подключения потребуется выбор провайдера PostgreSQL. Установка любых пакетов допускается только после разрешения пользователя согласно AGENTS.md; в рамках этого ТЗ пакеты не устанавливаются.

Архитектурный критерий: одна и та же запрещённая команда, отправленная из Blazor или будущего API, отклоняется одинаково; нарушение записи истории откатывает всю операцию завершения в PostgreSQL. REST API не является предварительным условием переноса реестра на постоянное хранение.

## 5. Интерфейс по корпоративной концепции №2

| ID | Решение | Проверяемый результат |
| --- | --- | --- |
| UI-01 | Постоянное боковое меню, верхняя строка предприятия и вошедшего пользователя, синий акцент и сдержанная плотная компоновка | Реестр, заявки, история и разрешённая сводка достижимы через навигацию; пользователь соответствует сеансу, демонстрационное имя не выдаётся за вход |
| UI-02 | Панель поиска, состояния и подразделения над табличным реестром | Видны активные условия и число найденных записей; очистка текста не снимает остальные фильтры |
| UI-03 | Таблица с четырьмя основными полями, действия по правам, формы добавления/неисправности/обработки | Пользователь проходит сквозной сценарий без обращения к БД вручную; обязательные поля подписаны; отправка блокируется до ответа |
| UI-04 | Карточки всего парка и блок обслуживания как вход в очередь | Руководитель получает показатели FR-07.1; переход из блока открывает очередь; для других ролей нет запрещённых значений сводки |
| UI-05 | Мобильная адаптация | На ширине 360 CSS px меню переносится вверх, таблица прокручивается внутри области; формы и действия доступны без обрезания |
| UI-06 | Доступность | Все действия выполняются клавиатурой, фокус виден, поля имеют label, статус передаётся текстом и цветом; счётчик/сообщения объявляются через aria-live; системное снижение анимации учитывается |
| UI-07 | Раздельные состояния загрузки, данных, пустого источника, пустого поиска, ошибки и переподключения | Каждое состояние воспроизводится независимо; при ошибке есть понятное восстановление, при фильтрации нет фиктивных данных |

HTML-концепция №2 — ориентир компоновки, а не источник реальных показателей, прав и бизнес-правил. Навигация к блокам макета переносится в доступные маршруты/компоненты приложения. Модель оборудования, демонстрационная загрузка и расширенный поиск макета не становятся обязательными полями семи историй. Новые подразделения требуют структурированного справочника, а не извлечения названия цеха из строки места установки.

Показатели производительности и восстановления не измерены на прототипе. SLA доступности, срок хранения истории/журналов, часовой пояс предприятия и точный профиль нагрузки требуют согласования перед эксплуатационной приёмкой. Несохранённый ввод сохраняется в доступном текущем сеансе; восстановление после потери серверного circuit или перезагрузки без специального механизма черновиков не гарантируется, о потере необходимо предупредить.

## 7. Обработка ошибок и восстановление

| Ситуация | Поведение и сообщение | Проверяемый результат / восстановление |
| --- | --- | --- |
| Пустой реестр / нет совпадений | «В реестре пока нет оборудования» / «Оборудование не найдено» | Состояния различаются; во втором случае условия сохранены, доступен сброс |
| Недоступен источник реестра, истории или сводки | «Не удалось загрузить …» и «Повторить» | Индикатор завершается; повтор сохраняет контекст; ошибка не выдаётся за пустоту или нули |
| Незаполненные поля или неверное состояние | Ошибки возле полей, сводка и фокус первой ошибки | Ни одна запись не создана; корректный ввод сохранён |
| Дублирующий номер | «Оборудование с таким инвентарным номером уже существует» | Ограничение БД отклоняет и конкурентный дубль; можно исправить только номер |
| Оборудование/заявка отсутствует | Понятное сообщение о недоступности | Нет записи без связи; описание сохраняется, предлагается обновить выбор |
| Пустая очередь / история | «Заявок пока нет» / «История обслуживания отсутствует» | Нет демонстрационных строк; ошибка источника имеет другое состояние |
| Пустое завершение / неверный переход | Ошибки обязательных полей / «Недопустимый переход статуса» | Статус и история неизменны; доступны только разрешённые действия |
| Конкурентная команда | «Заявка изменена другим пользователем. Обновите данные» | Чужие изменения не перезаписаны; черновик сохранён в доступном сеансе |
| Ошибка транзакции завершения | «Не удалось завершить заявку. Статус и история не изменены» | Это сообщение допустимо только при подтверждённом откате; повтор создаёт максимум одну историю |
| Нет сеанса / нет прав | «Войдите в систему» / «У вас нет прав на выполнение этого действия» | Никаких защищённых изменений; вход возвращает на исходный разрешённый адрес |
| Подтверждённый отказ сохранения | «Не удалось сохранить данные. Повторите попытку» | Нет ложного успеха и фиктивной строки; ввод сохранён, повтор доступен |
| Ответ потерян, исход неизвестен | «Подтверждение не получено. Проверяем результат операции» | Нельзя обещать откат; сверка по ID операции предшествует безопасному повтору |
| Потеря соединения Blazor | «Соединение с сервером потеряно. Восстанавливаем подключение» | Изменения временно блокируются; после восстановления данные сверяются; перед перезагрузкой предупреждение о вводе |
| Неожиданное исключение | Русское сообщение и ID обращения | Исключение зарегистрировано; стек и секреты не раскрываются; общая /Error дополняет локальную обработку |

Проверка ошибок проводится через имитацию отказа источника, потери ответа, истечения сеанса и конкурентных команд. Наличие общей страницы /Error само по себе не подтверждает выполнение этих требований.

| GWT-02 | Два специалиста прочитали одну версию заявки | Оба завершают | Одна история, второй получает конфликт либо сохранённый результат своей повторной операции |

| GWT-04 | Сеанс истёк перед отправкой | Выполнена команда | 401/переход ко входу, изменение не выполнено, чужие данные не раскрыты |
| GWT-05 | Соединение Interactive Server потеряно | Пользователь пытается сохранить | Команда блокируется; после восстановления выполняется сверка, нет ложного успеха |

При реализации US-07 руководитель после обновления видит уменьшение числа открытых заявок. Каждый этап проверяется также через отказ сервера и соответствующую запрещённую роль.

## 9. Хранение данных и будущий REST API

### 9.1. Предлагаемая логическая модель PostgreSQL

| ID / сущность | Основные поля и связи | Ограничения и проверяемый результат |
| --- | --- | --- |
| DATA-01 / Equipment | Id, Name, InventoryNumber, NormalizedInventoryNumber, Location, TechnicalStatus, DepartmentId?, Version | PK, обязательность полей FR-03.2, уникальность нормализованного номера; две одинаковые нормализованные записи невозможны |
| DATA-02 / Department | Id, Name | FK оборудования на подразделение; имя для фильтра не вычисляется из Location; нераспределённые записи видимы в «Все» и предлагаемой группе «Не указано» |
| DATA-03 / FaultRequest | Id, EquipmentId, Description, Status, CreatedBy, CreatedAt, AssignedTo?, UpdatedAt, Version | FK на оборудование и пользователей; допустимые статусы; автор/дата серверные; заявки без оборудования невозможны |
| DATA-04 / RequestTransition | Id, RequestId, FromStatus, ToStatus, ActorId, OccurredAt | Каждая успешная смена сохраняет автора и время в той же транзакции; аудит последовательности доступен для проверки |
| DATA-05 / MaintenanceRecord | Id, RequestId, EquipmentId, PerformedAt, WorkDescription, Result, PerformedBy | UNIQUE(RequestId), обязательные работы/результат; история относится к оборудованию исходной заявки; ровно одна история завершения |
| DATA-06 / User, UserRole | Внутренний ID, внешний subject поставщика входа, отображаемое имя, назначенные роли | Внешний subject уникален; роли не принимаются из произвольного тела запроса; аудит не теряет автора при отключении учётной записи |
| DATA-07 / Operation | OperationId, ActorId, CommandType, PayloadHash, State, ResultReference, CreatedAt | Уникальный ключ в области пользователя и команды; результат фиксируется вместе с бизнес-изменением; повтор не дублирует операцию |

Существующий Equipment.Id имеет тип int; предлагается сохранить его, не требуя миграции на другой тип без причины. Новые идентификаторы могут быть bigint/UUID по выбранной схеме, до фиксации API. Даты — timestamptz, серверный UTC. Необязательные поля обозначены «?», остальные обязательны по назначению. Длины строк, формат номера, допустимые символы и сроки хранения не устанавливаются произвольно: их следует согласовать отдельно.

DATA-08. Нормализация номера: убрать крайние пробелы и применить единое сравнение без учёта регистра. При реализации выбрать детерминированный алгоритм Unicode и одинаковую семантику в C# и БД; PostgreSQL lower/trim нельзя автоматически считать точным эквивалентом .NET Trim и сравнения текущей культуры. Приёмка включает латиницу, кириллицу, смешанный регистр и крайние пробельные символы. До выбора алгоритма минимум исходных примеров INV-1001 обязателен; расширенный набор необходимо зафиксировать перед миграцией.

DATA-09. Завершение, запись истории, аудит и результат операции сохраняются одной транзакцией. Version проверяется при изменении; уникальное ограничение RequestId защищает от двойного завершения. Ограничения FK и UNIQUE дополняют серверные правила. Несоответствие EquipmentId истории и заявки исключается связью через заявку либо составным внешним ключом; одной проверки формы недостаточно.

DATA-10. Удаление не является пользовательской функцией данного объёма; каскадное уничтожение заявок/истории запрещается. FK ограничивает удаление связанных объектов. Сценарий отсутствующего объекта всё равно обрабатывается для устаревших ссылок, миграций и административных изменений. Индексы предусматриваются по нормализованному номеру, EquipmentId, статусу заявки и дате истории. Необходимость полнотекстового/trigram-индекса определяется измерениями, без автоматической установки расширений.

### 9.2. Предлагаемый REST API ASP.NET Core

API пока отсутствует; приведён проект контрактов приложения, а не перечень существующих маршрутов Supabase. Базовый путь `/api/v1`. Бизнес-правила общие с Blazor. На первом этапе Blazor может обращаться к сервисам напрямую.

| ID | Метод и путь | Доступ и проверяемый результат |
| --- | --- | --- |
| API-01 | GET /equipment?query=&status=&departmentId=&page=&pageSize= | Все роли; элементы четырёх полей, ID, подразделение, версия, totalCount; совместные условия FR-02; успешная пустота 200 |
| API-02 | GET /equipment/{id} | Все роли; объект 200 либо 404 |
| API-03 | POST /equipment | Инженер; корректная запись 201 с ID и Location; дубликат 409 |
| API-04 | GET /departments | Все роли; справочник фильтра 200, пустой справочник без демонстрационных значений |
| API-05 | POST /fault-requests | Инженер/специалист; EquipmentId и Description → 201, «Новая», автор/время сервера |
| API-06 | GET /fault-requests и GET /fault-requests/{id} | Все роли; очередь/карточка 200; отсутствующий ID 404 |
| API-07 | POST /fault-requests/{id}/start | Специалист; ожидаемая версия → 200, статус и новая версия; конфликт 409 |
| API-08 | POST /fault-requests/{id}/complete | Специалист; версия, работы, результат → 200, завершённая заявка и ID единственной истории |
| API-09 | GET /equipment/{id}/maintenance-history | Все роли; 200, только история выбранного объекта по убыванию даты; пустая история []; отсутствующее оборудование 404 |
| API-10 | GET /summary | Руководитель; 200 с totalEquipment, openRequests, inProgressRequests и временем снимка; без параметров фильтра реестра |
| API-11 | GET /operations/{operationId} | Владелец операции; состояние и результат 200; чужой/неизвестный ID не раскрывает данные |

API-12. Для изменяющих POST предлагается обязательный Idempotency-Key. Повтор с тем же телом возвращает сохранённый результат; ключ с другим телом — 409. До отправки клиент создаёт и сохраняет ID операции в пределах допустимого сеанса; сервер не полагается на отключение кнопки. Политика срока хранения ключей должна покрывать допустимый период повторов и быть согласована до выпуска API.

API-13. Ошибки оформляются ProblemDetails с устойчивым code, traceId и errors для полей: 400 — валидация/неверный формат, 401 — нет действительного сеанса, 403 — недостаточно прав, 404 — объект отсутствует, 409 — дубликат/версия/переход, 500 — неожиданная ошибка, 503 — временная недоступность зависимости. Ответ не содержит секретов и стека; клиент выбирает русское сообщение по коду. Бизнес-сбой и пустой результат имеют разные ответы. Потеря HTTP-ответа не доказывает откат.

API-14. Пагинация, размер страницы и стабильная сортировка нужны при росте данных; предлагаются pageSize по умолчанию 50, максимум 100, сортировка реестра по ID, истории по дате и ID по убыванию. Это новые проектные параметры, а не ограничения исходных документов. totalCount относится ко всей отфильтрованной выборке; при пагинации UI показывает «Показано N из M», сохраняя понятный смысл счётчика. Требование «счётчик равен числу строк» исходных AC принимается для режима без пагинации; изменение этого режима требует согласования, а не молчаливой подмены AC.

Контракты DTO, OpenAPI, схема входа, ограничения запросов и политика обновления токенов оформляются при реализации; документация API и тесты должны подтверждать ту же матрицу прав и AC. PATCH/PUT для редактирования и DELETE не входят в перечисленные семь историй.

## 12. Итоги проверки полноты и реализуемости

Полнота: покрыты 7 из 7 US и 28 из 28 исходных AC, включая успешный, негативный и граничный результаты. Для каждой функциональной группы определены наблюдаемый результат, права, данные и реакция на отказ; дополнительные сетевые/конкурентные проверки вынесены в GWT-01–GWT-08. Корпоративная концепция, PostgreSQL/Supabase, будущий API, фактический прототип и дальнейшее развитие разделены явно.

Согласованность: выявлены 9 расхождений/коллизий, перечисленных отдельно с исправлениями. Основные блокирующие решения перед полноценной реализацией форм — справочник технических состояний, модель подразделений и граница MVP по редактированию/фильтру Location. Дополнительно согласуются поставщик входа и назначение ролей, право изменения исполнителя, алгоритм Unicode-нормализации, ограничения строк, профиль нагрузки, хранение истории/ключей операций и эксплуатационные цели. Наличие открытых решений не означает, что исходные документы уже исправлены.

Реализуемость: целевой процесс технически реализуем на C#, .NET 9, ASP.NET Core, Blazor и одном PostgreSQL, в том числе размещённом в Supabase. Атомарность требует одной транзакции на стороне БД/сервера, а не последовательных независимых запросов браузера; конкурентность — версий и ограничений; повторные команды — идентификаторов операций. Interactive Server требует отдельной обработки потери соединения и не обеспечивает автоматически долговечность черновика. Реализуемость заданных показателей производительности/восстановления должна быть подтверждена измерениями и доступной инфраструктурой, а не только выбором стека.

Предлагаемый порядок: согласовать блокирующие справочники и объём → хранилище и права → реестр/добавление/поиск → заявки и транзакционное завершение → история и негативные проверки → сводка Should have → REST API и согласованное развитие EXT. Без сроков, состава команды и стенда оценка трудоёмкости и календарная дата готовности не устанавливаются.

Критерий завершения этапа семи историй: приняты все соответствующие AC, дополнительные обязательные механизмы безопасности/целостности и согласованные NFR; US-07 принимается отдельно как Should have. Это проверка будущей реализации. Настоящая работа создаёт только техническое задание и не подтверждает готовность этих функций в прототипе.
