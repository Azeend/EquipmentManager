# EquipmentManager — лабораторная работа №2

## Описание и назначение

EquipmentManager — веб-приложение для учёта промышленного оборудования. Оно предназначено для просмотра сведений об оборудовании, поиска нужной единицы и контроля её места установки и технического состояния.

## Основные функции

В текущем проекте реализованы:

- Модель оборудования с идентификатором, наименованием, инвентарным номером, местом установки и состоянием.
- Страница `/equipment` с таблицей оборудования.
- Поиск по наименованию и инвентарному номеру без учёта регистра.
- Получение демонстрационных данных через `EquipmentDataService`.
- Отдельный валидатор обязательных полей и допустимых состояний оборудования. Его подключение к операциям сохранения потребуется при их реализации.

Планируется добавить постоянное хранение данных в PostgreSQL и операции добавления, редактирования и удаления оборудования. Эти возможности относятся к развитию проекта и пока не реализованы.

## Технологический стек

- C# — язык разработки.
- .NET 9 — целевая платформа (`net9.0`), с включёнными nullable reference types.
- ASP.NET Core — веб-хост, внедрение зависимостей и обработка HTTP-запросов.
- Blazor — пользовательский интерфейс на Razor-компонентах; в проекте настроена поддержка Interactive Server.
- PostgreSQL — планируемая база данных; сейчас используются демонстрационные данные в памяти. Провайдер и способ доступа к PostgreSQL выбираются на этапе реализации, установка пакетов требует согласования.

## Требования к архитектуре

- Сохранять существующую структуру проекта: `Components` для интерфейса, `Models` для моделей, `Services` для сервисов, `Validators` для проверок данных.
- Разделять представление, бизнес-логику, валидацию и доступ к данным; не размещать SQL и логику хранения в Razor-компонентах.
- Передавать сервисы через встроенный механизм внедрения зависимостей ASP.NET Core.
- При подключении PostgreSQL изолировать доступ к базе в соответствующем слое и использовать асинхронные операции ввода-вывода.
- Проверять данные на сервере перед сохранением; согласовать допустимые состояния между моделью, интерфейсом, валидатором и будущей базой данных.
- Изменять только файлы, относящиеся к поставленной задаче, и сохранять компилируемость проекта.

## Требования к стилю кода

- Использовать PascalCase для классов и публичных свойств, camelCase для локальных переменных.
- Соблюдать nullable reference type safety: явно описывать допустимость `null`, проверять входные значения и корректно инициализировать свойства.
- Добавлять XML-комментарии на русском языке.
- Объяснять решения и результаты на русском языке и перечислять все изменённые файлы.
- Не устанавливать пакеты без согласования.

## Требования к безопасности

- Не записывать пароли, API-ключи и другие секреты в исходный код или репозиторий. Для локальной разработки использовать User Secrets, для развёртывания — переменные окружения или защищённое хранилище секретов.
- При подключении PostgreSQL хранить строку подключения с секретами вне репозитория и предоставлять приложению минимально необходимые права базы данных.
- Использовать параметризованные запросы либо безопасные средства доступа к данным; не формировать SQL конкатенацией пользовательского ввода.
- Сохранять HTTPS, защиту от подделки запросов и безопасный вывод пользовательских данных средствами Razor.
- При реализации операций изменения данных предусмотреть аутентификацию и проверку прав на сервере.
- Не игнорировать исключения: обрабатывать их на подходящем уровне и регистрировать диагностические сведения без секретов; не раскрывать пользователю внутренние детали ошибок.
