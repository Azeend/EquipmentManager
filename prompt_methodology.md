# Лабораторная работа №2. Методика пошаговой проверки поиска

## Объект и условия работы

Проект EquipmentManager на .NET 9, страница `Components/Pages/EquipmentList.razor`. Проверялся поиск оборудования по названию (`Name`) и инвентарному номеру (`InventoryNumber`).

Существующий код приложения не изменялся, поскольку требуемая функциональность уже была реализована. Выводы анализа исходного кода, результаты сборки и ручной проверки разделены ниже.

## Этап 1. Анализ существующей реализации поиска

### Цель

Установить, реализован ли поиск по названию и инвентарному номеру, прежде чем предлагать изменения.

### Фактически использованный промпт

Оригинальный промпт первого этапа предоставлен пользователем при дополнении документации:

```text
**Role:** Ты опытный архитектор C# и Blazor-приложений.
**Task:** Изучи существующую страницу `Components/Pages/EquipmentList.razor`, модель `Models/Equipment.cs` и сервис `Services/EquipmentDataService.cs`. Разбей реализацию поиска оборудования на три логических этапа: анализ существующей реализации, добавление или исправление фильтрации, проверка и обработка граничных случаев.
**Context:** Проект EquipmentManager на .NET 9 и Blazor. Страница `/equipment` уже отображает пять единиц оборудования. Поиск должен работать по `Name` и `InventoryNumber` без учёта регистра, обновляться при каждом вводимом символе и показывать сообщение «Оборудование не найдено», если совпадений нет. Учитывай `AGENTS.md` и фактический режим рендеринга Blazor.
**Format:** Составь краткий план из трёх этапов. Для каждого укажи изменяемые файлы, действия и критерии проверки. Сначала определи, какие из требований уже реализованы. Ничего в проекте пока не изменяй.
```

### Действия Codex

Подробности первоначального анализа в доступной истории не представлены. При последующих проверках Codex прочитал `EquipmentList.razor` и подтвердил наличие свойства `FilteredEquipment`, которое фильтрует исходную коллекцию через `Where` и проверяет `Contains` для обоих полей, объединяя условия оператором `||`.

### Полученные результаты

Поиск по обоим полям уже существовал. Для включения записи в результат достаточно совпадения в любом из них. Оснований добавлять новую реализацию поиска не выявлено.

## Этап 2. Проверка функциональности

### Цель

Проверить соответствие реализации требованиям: отсутствие зависимости от регистра, обновление при вводе, полный список при пустом запросе и сообщение при отсутствии совпадений.

### Фактически использованный промпт

```text
**Role:** Ты опытный C# и Blazor-разработчик.
**Task:** Проведи второй этап пошаговой проверки страницы EquipmentList.razor.
**Context:** Предыдущий анализ показал, что поиск по Name и InventoryNumber уже реализован. Проверь его соответствие требованиям: поиск без учёта регистра, фильтрация при вводе каждого символа, отображение всех записей при пустом запросе и сообщение при отсутствии результатов.
**Format:** Составь таблицу «Требование — Реализация — Результат анализа». Отдельно укажи, какие сценарии требуют ручной проверки в браузере. Не изменяй исходный код и не заявляй о выполненном тестировании, если его не проводил.
```

### Действия Codex

- Прочитал инструкции `AGENTS.md` и код `EquipmentList.razor`.
- Проверил сравнение строк, привязку поля ввода, обработку пустого запроса и ветку вывода сообщения.
- Проверил связанные настройки интерактивности в `Components/App.razor` и `Program.cs`, модель и данные сервиса.
- Составил таблицу соответствия требованиям и список сценариев для браузера.

### Полученные результаты

| Требование | Реализация | Вывод по коду |
|---|---|---|
| Поиск по двум полям | `Name.Contains(...) || InventoryNumber.Contains(...)` | Реализован |
| Без учёта регистра | `StringComparison.CurrentCultureIgnoreCase` | Реализован с учётом текущей культуры |
| Обновление при вводе | `@bind:event="oninput"`; для `Routes` включён `InteractiveServer` | Предусмотрено реализацией |
| Все записи при пустом запросе | `string.IsNullOrWhiteSpace(searchQuery)` возвращает `allEquipment` | Реализовано |
| Сообщение при отсутствии результатов | При `FilteredEquipment.Count == 0` выводится «Оборудование не найдено» | Реализовано |

На этом этапе Codex выполнил статический анализ. Сборка и браузерное тестирование в рамках этого этапа не проводились.

## Этап 3. Проверка граничных случаев и сборки

### Цель

Проверить обработку пустого запроса, пробелов, частичных совпадений и отсутствия результатов, а также фактически выполнить сборку проекта.

### Фактически использованный промпт

Следующий промпт был отправлен пользователем дважды; Codex выполнил первоначальную и повторную проверку:

```text
**Role:** Ты инженер по тестированию C# и Blazor-приложений.
**Task:** Выполни заключительную проверку поиска оборудования в EquipmentManager.
**Context:** Страница EquipmentList.razor уже содержит поиск по названию и инвентарному номеру. Требуется проверить пустой запрос, строку из пробелов, пробелы по краям, частичные совпадения и отсутствие результатов.
**Format:** Проанализируй реализацию, составь таблицу проверок, выполни dotnet build и сообщи фактические результаты. Не изменяй код без обнаружения ошибки. Отдельно укажи, какие проверки выполнены анализом кода, а какие требуют тестирования в браузере.
```

### Действия Codex

- Повторно прочитал реализацию поиска и текущий набор данных `EquipmentDataService` из пяти записей.
- Проанализировал `IsNullOrWhiteSpace`, `Trim`, `Contains` и условие отображения сообщения.
- Составил таблицу сценариев с ожидаемыми результатами по коду.
- Выполнил `dotnet build` и зафиксировал фактический вывод команды.

### Полученные результаты анализа

| Сценарий | Пример запроса | Результат, следующий из кода и текущих данных |
|---|---|---|
| Пустой запрос | `""` | Все 5 записей |
| Только пробелы | `"   "` | Все 5 записей |
| Пробелы по краям | `"  насос  "` | После `Trim()` результат совпадает с `"насос"`: одна запись |
| Частичное название | `"нас"` | «Центробежный насос ЦНС 180-85» |

### Фактические результаты сборки

При первом выполнении `dotnet build` сборка завершилась с 2 ошибками и 12 предупреждениями: исполняемый файл был занят другим процессом (`MSB3027`, `MSB3021`). Повторная сборка с отдельным каталогом вывода командой `dotnet build EquipmentManager.csproj -o .build-search-check` завершилась успешно: 0 ошибок, 2 предупреждения `NU1900`.

При последней проверке обычная команда `dotnet build` также завершилась успешно:

| Показатель | Фактический результат последнего запуска |
|---|---|
| Код завершения | `0` |
| Ошибки | `0` |
| Предупреждения | `2`, оба `NU1900` |
| Время по выводу сборки | `2,47 с` |
| Выходная сборка | `bin/Debug/net9.0/EquipmentManager.dll` |

Предупреждения `NU1900` означают, что не удалось получить данные об уязвимостях пакетов из `https://api.nuget.org/v3/index.json`. Успешная сборка не подтверждает выполнение проверки уязвимостей или функциональных тестов.
